## Findings

### <a id="r-01"></a>R‑01 — Authorization state is re-fetched per check, several times per request  **[critical]**

**Evidence.**
- `internal/authorization/application/service.go` — `Decide` runs `IsActiveInstanceAdmin` +
  `ActiveGrantsForSubject` (two queries) on every call; the comment at ~line 89 states
  "Decisions are not cached across requests."
- `internal/authorization/pep/pep.go` — `RequireAny` loops calling `Enforce`, i.e. N full
  `Decide` round-trip sets for one gate.
- `internal/identityfederation/middleware/authenticator.go` (~line 140) — the authenticator
  additionally calls `RLSStateFor` (→ `EffectiveReach` → the same two queries again + closure
  expansion) on **every authenticated request**, before the handler runs its own `Require`.

So a typical guarded request pays ≥3 executions of the grants join
(`authz_role_assignments ⋈ authz_roles ⋈ authz_role_permissions`) plus closure probes — before any
business query. There is no request-scoped memoization, let alone cross-request caching.

**Why it breaks at target scale.** PDP load is per-request multiplicative. At national scale
(thousands of RPS, subjects with tens of grants), authorization becomes the dominant DB load and
its latency is serialized in front of every handler.

**Fix sketch (do together with R‑02/R‑03/R‑04 — see roadmap Phase 1).**
1. **Request-scoped authority context**: the authenticator already resolves the subject; have it
   fetch `(isAdmin, grants)` once, stash in `context` (alongside `pkg/authn`'s subject), and make
   `Decide`/`EffectiveReach`/`FilterVisibleUnits` consume it. This is a pure refactor — semantics
   are identical (state is a snapshot at request start, which is already true per-call today).
2. **Cross-request cache (second step, needs a decision amendment)**: short-TTL (1–5 s) cache of
   `(subject → grants, isAdmin)` keyed by a revocation epoch — a single `authz_epoch` counter
   bumped in the grant/revoke/role-edit transactions makes invalidation exact and cheap
   (one indexed read to validate a hit). The "a revoke takes effect on the next call" property in
   the code comment is preserved to within the TTL; record the chosen bound in `decisions.md`.

**Acceptance.** A guarded read endpoint issues exactly one grants fetch per request (verify with
`pg_stat_statements` or a pgx tracer in an integration test); PDP bench
(`internal/authorization/domain/pdp_bench_test.go`) extended with an application-level benchmark
showing decision cost independent of the number of `Require*` calls in a request.

### <a id="r-02"></a>R‑02 — Reach is materialized app-side and shipped as comma-joined GUC strings  **[critical]**

**Evidence.**
- `internal/authorization/domain/pdp.go` — `ReachSet` expands a subtree grant into **all
  descendant unit IDs** via `DescendantUnitIDs` and returns them as Go maps.
- `internal/platform/db/rls.go` — `setRLSGUCs` comma-joins `ReadableUnits`/`WritableUnits` into
  the `app.readable_units` / `app.writable_units` session GUCs.
- `migrations/20260601000011_rls_backstop.sql` — policies filter with
  `col = ANY (string_to_array(current_setting('app.readable_units', …), ',')::uuid[])`.
- `internal/person/application/service.go` — `ListVisiblePersons` flattens `reach.Readable` into
  a `[]string` and passes it as an array parameter to
  `ActivePersonIDsInUnits` (`internal/membership/adapters/queries/membership.sql`,
  `WHERE unit_id = ANY(@unit_ids::uuid[])`).

**Why it breaks at target scale.** A staff-level subject with a subtree grant near an org root has
reach ≈ the whole org: 10⁴–10⁵ unit RIDs. Per request that is: one closure query returning 10⁵
rows → a Go map → a multi-megabyte GUC string set over the wire → per-statement re-parse
(`string_to_array` on a huge string) → linear `= ANY` scans per row in every RLS-guarded
statement → 10⁵-element array parameters on the membership union. Memory, network, parse and plan
cost all scale with org size **per request**.

**Fix sketch.** Invert the direction: stop exporting the reach set out of the database.
1. Replace app-side reach materialization with **SQL semi-joins**: the visible-persons union
   becomes one query joining `membership_memberships` → `tenant_unit_closure` →
   `authz_role_assignments` on the subject (grants: `unit` scope matches unit directly, `subtree`
   scope matches via closure `ancestor_id = target_unit_id`). Same shape for the shadow gate.
   `ReachSet` stays only for small-cardinality callers (or is deleted).
2. Re-shape the RLS backstop (amends **D-RLSDefenseInDepth**): the GUC carries only
   `app.person_id` + `app.is_instance_admin`; policies check reach with an
   `EXISTS (… closure ⋈ assignments …)` sub-select (Postgres caches the plan; the closure PK
   `(graph_id, ancestor_id, descendant_id)` and `tenant_unit_closure_descendant_idx` make each
   probe an index hit). This keeps the backstop exact under revocation (better than today's
   snapshot-at-request-start) and drops the GUC size to O(1).
3. Add the missing reverse-direction support index if EXPLAIN shows it:
   `authz_role_assignments (subject_person_id) WHERE revoked_at IS NULL` (verify what exists in
   `migrations/20260601000007_authorization.sql` first).

**Acceptance.** No GUC ever contains a unit list; `GET /persons` for a subject whose reach is a
100k-unit subtree runs in O(page) — demonstrated by an integration test that seeds a synthetic
10⁵-unit graph (generator script, keep under `scripts/`) and asserts p95 latency and
`pg_stat_statements` row counts; RLS policies validated by the existing
`internal/platform/db/rls_integration_test.go` extended to the new policy shape.

### <a id="r-03"></a>R‑03 — Every authenticated request pins a pooled connection for its full duration  **[critical]**

**Evidence.** `internal/identityfederation/middleware/authenticator.go` (~line 145) calls
`db.AcquireScoped` per request; `internal/platform/db/rls.go` shows the cost: 4 × `set_config`
round trips on acquire + 4 × on release, and the connection is held in the request context until
the response is written — including across **external HTTP calls** (the watchlist screen, R‑12)
and across handler work that never touches an RLS-guarded table (only 4 tables have policies —
see `migrations/20260601000011_rls_backstop.sql`).

**Why it breaks at target scale.** Concurrent requests ≈ pinned connections. A pgx pool of, say,
50 conns caps the server at ~50 in-flight requests regardless of how little DB work they do; one
slow downstream (hermenea) or a burst of long list queries exhausts the pool for everyone. The 8
extra round trips are pure per-request tax.

**Fix sketch.**
1. If R‑02 lands, the GUC state is two tiny values — set them with **one** round trip
   (`SELECT set_config('app.person_id',$1,true), set_config('app.is_instance_admin',$2,true)`
   with `is_local=true` inside the statement's transaction, or a single batched exec).
2. Scope pinning to need: pin lazily — only when a handler actually acquires the querier for one
   of the RLS-guarded modules (`internal/platform/db/rls.go` already routes through
   `WithConn`/`ConnFromContext`; move `AcquireScoped` behind the first `querier(ctx)` call and
   release on handler return, not on response write).
3. Never hold the pinned conn across the hermenea egress (`person/application/watchlist.go`
   path): screen first or release before the outbound call.

**Acceptance.** A load test (even `hey`/`vegeta` against a read endpoint) shows in-flight request
concurrency exceeding pool size; per-request DB round-trip count for a non-RLS endpoint (e.g.
`GET /geo/countries`) drops by 8.

### <a id="r-04"></a>R‑04 — Closure is fully rebuilt inside every edge-change transaction  **[critical]**

**Evidence.** `internal/tenant/adapters/queries/tenant.sql` (header comment: "transitive closure
recomputed in the write transaction on every edge change"; ~line 269 `DELETE FROM
oikumenea.tenant_unit_closure WHERE graph_id = @graph_id` + `RebuildClosureForGraph` recursive
insert). Called from `Repository.RecomputeClosure`
(`internal/tenant/adapters/repository.go` ~line 300) in the caller's write tx.

**Why it breaks at target scale.** Closure size for a 10⁵-unit graph of depth ~8 is ~10⁶ rows.
Every single edge attach/detach deletes and reinserts all of them inside the user-facing write
transaction: seconds-to-minutes of latency, a giant WAL burst, table/index bloat from full
churn, and effective serialization of all structural edits on a graph (the DELETE takes a lock
footprint that conflicts with concurrent readers of the same graph's closure via the PDP —
i.e. **authorization decisions stall while anyone edits the org chart**).

**Fix sketch (amends the maintenance strategy behind D-Graphs / D-ClosureIntegrity; the
decision's *contract* — a materialized closure the PDP reads — stays).**
- Incremental maintenance, standard DAG closure algebra:
  - **attach(parent, child):** `INSERT … SELECT anc.ancestor_id, desc.descendant_id, anc.depth +
    desc.depth + 1 FROM closure anc, closure desc WHERE anc.descendant_id = parent AND
    desc.ancestor_id = child ON CONFLICT DO NOTHING` (multi-parent DAG ⇒ closure rows are a set;
    if `depth` must stay minimal, use `ON CONFLICT … DO UPDATE SET depth = LEAST(...)`, or drop
    depth-precision — audit whether anything reads `depth`; the PDP does not).
  - **detach:** the hard direction in a DAG (alternative paths). Recompute only the **affected
    sub-closure**: rows `(a,d)` where `a ∈ ancestors(parent) ∪ {parent}` and
    `d ∈ descendants(child) ∪ {child}` — delete those pairs, re-derive them from edges with one
    recursive CTE bounded to that slice. For non-root detaches this is orders of magnitude
    smaller than the whole graph.
- Keep `RebuildClosureForGraph` as the D-ClosureIntegrity repair/verify path (that decision
  explicitly wants an on-demand rebuild — it just must stop being the per-edit path).

**Acceptance.** Property test (mirror the style of
`internal/authorization/domain/pdp_property_test.go`): random edge attach/detach sequences on a
random DAG — incremental closure ≡ from-scratch recompute after every step. Bench: single edge
attach on a synthetic 50k-unit graph touches O(ancestors × descendants-of-child) rows, not O(graph).

### <a id="r-05"></a>R‑05 — Import path: whole dataset per POST, one transaction, row-at-a-time upserts  **[high]**

**Evidence.**
- `internal/hermenea/loader/loader.go` — one `Load` = the entire dataset as a single JSON
  envelope; `httpclient.WithHTTPTimeout(0)` with a comment acknowledging the 27k-languoid POST
  "rebuilds the closure + family_code in a single transaction — well past conjure's 60s default".
- `internal/dataimport/application/service.go` — every handler is `for _, rec := range records`
  with per-record upserts (11 such loops); no `CopyFrom`, no chunking, one tx per envelope.

**Why it breaks at target scale.** Proven ceiling so far is 35k records. National-scale reference
data (full multi-country gazetteers, consolidated sanctions, company registries) is 10⁶–10⁷
records: the envelope alone is GBs of JSON held in memory on both sides, the single transaction
holds locks and bloats for hours, and a failure at record N loses all progress (hermenea's retry
re-sends everything).

**Fix sketch.**
1. **Chunked envelopes**: extend the import contract (`api/*.conjure.yml` for dataimport) with
   `(runId, seq, isLast)`; hermenea's connector streams chunks of ~5k records; oikumenea commits
   per chunk. Idempotency already exists per record (natural-key upserts + provenance), so chunk
   replay is safe — resumability falls out for free (store last-acked `seq` on the job).
2. **Set-based apply** inside a chunk: `CopyFrom` into a temp staging table + one
   `INSERT … SELECT … ON CONFLICT` merge per target table, replacing the per-record loop for the
   high-volume object types (geo-places, language-scheme, external-organizations, sanctions).
   Low-volume types can keep the simple loop.
3. Restore a real HTTP deadline on the loader once no single request carries a whole dataset.

**Acceptance.** A 1M-record synthetic geo-places import completes with bounded memory (< a few
hundred MB RSS on both binaries), survives a kill -9 of either side mid-run and resumes, and no
transaction lives longer than ~seconds. Existing e2e (compose run) still green.

### <a id="r-06"></a>R‑06 — Person search: un-indexed `ILIKE '%q%'`, and Go-side filtering after pagination  **[high]**

**Evidence.**
- `internal/person/adapters/queries/person.sql` — `ListPersons` filters
  `display_name/code/given/surname ILIKE '%' || @query || '%'`; `grep pg_trgm\|GIN migrations/`
  comes back empty — no trigram or FTS index anywhere.
- `internal/person/application/service.go` — `ListVisiblePersons` applies the text query **in Go
  to the already-paginated page** (comment at ~line 375): a page may legitimately return 0
  matches while `nextPageToken` is set, so a scoped search for a rare name pages through the
  entire visible roster one page at a time.

**Why it breaks at target scale.** Leading-wildcard `ILIKE` over four columns at 1M rows is a
sequential scan per keystroke of the console's typeahead. The scoped path is worse: correctness
degrades (empty pages) and worst-case cost is O(visible-set / pageSize) round trips.

**Fix sketch.**
1. Migration: `CREATE EXTENSION IF NOT EXISTS pg_trgm;` + one GIN trigram index over a generated
   concatenated search column (or one index per column; measure), partial `WHERE deleted_at IS NULL`.
2. Fold the query into the SQL of the scoped path: after R‑02 the visible list is one SQL join —
   add the trigram predicate there, keyset cursor stays on person RID. Delete
   `matchesPersonQuery`.

**Acceptance.** `EXPLAIN (ANALYZE)` on a 1M-row seeded `person_persons` shows bitmap index scan
for a 3-char query; scoped search never returns an empty page while `hasMore` unless the true
result is empty.

### <a id="r-07"></a>R‑07 — `audit_log`: unpartitioned, 6 secondary indexes, unbounded, written in every tx  **[high]**

**Evidence.** `migrations/20260601000001_audit_log.sql` — 6 `CREATE INDEX` statements; no
partitioning anywhere (`grep -i partition migrations/*.sql` → no DDL hits); D-Audit mandates a
synchronous in-tx audit row for **every** write; append-only guard (`reject_mutation`) means it
only ever grows.

**Why it breaks at target scale.** The audit table becomes the largest, hottest table in the
system: 6 index maintenance operations added to every write transaction's critical path, and
years of national-scale writes with no retention/archival story make it the dominant storage,
vacuum, and backup cost. (D-Audit's *semantics* — same-tx, append-only — are right and are not
challenged; the physical layout is.)

**Fix sketch.**
1. Declarative **monthly range partitioning** on `created_at`. This edits a shipped migration or
   (better, per upgrade-safety) lands as an expand/contract migration: create partitioned
   `audit_log_v2`, dual-write via the repository for one release, backfill, swap names. Note the
   keyset cursor `(created_at DESC, id DESC)` is partition-friendly.
2. Cut indexes to what the read API actually serves (check
   `internal/audit/adapters/queries/audit.sql`): `(created_at,id)` + `(target_type,target_id)` +
   `(actor_person_id)` are probably the keepers; `actor_type`/`request_id`/`unit_id` singles are
   candidates to drop or fold into composites.
3. Retention: an operator-configured archival policy (detach + dump partitions older than N
   months). Record as a new decision (D-AuditRetention) — legal-hold requirements belong to the
   operator, so make it config, not code.

**Acceptance.** `pgbench`-style mixed write load shows reduced per-write latency vs baseline;
partitions detach/attach cleanly in a rehearsal; `atlas migrate lint` gate still passes
(expand/contract, nothing destructive in-place).

### <a id="r-08"></a>R‑08 — One sqlc config generates the whole schema into every module package  **[high]**

**Evidence.** Root `sqlc.yaml`: 16 codegen blocks, each with `schema: migrations` (the full
directory). Result: `internal/<module>/adapters/<m>sql/models.go` is ~2,997 lines in **17**
packages — each contains structs for every table in the system (e.g.
`OikumeneaTenantUnit` and `OikumeneaAuditLog` inside `personsql/models.go`). ~50k lines of
duplicated generated code; `git status` in memory notes a past incident of "reverted 14
non-tenant `*sql/models.go` sqlc churn" — every migration touches all modules' generated files.

**Why it matters.** (a) The hexagonal boundary is enforced socially, not mechanically: any module
can silently write a query against another module's tables and sqlc will happily generate it —
the exact bug class the architecture exists to prevent. (b) Every migration churns 17 files ×
3k lines, polluting diffs and inviting the "revert the churn by hand" failure mode already hit
once. (c) Compile-time and review cost grow with schema × modules.

**Fix sketch.** sqlc can't natively scope a schema dir per package, so pick one:
- **Option A (recommended, no codegen change):** a CI/lint script (`scripts/check-module-tables.sh`)
  that greps each module's `queries/*.sql` for `oikumenea.<prefix>_` table references and fails on
  a table outside the module's own prefix (plus an explicit, reviewed allowlist for the known
  cross-module reads, e.g. authorization → `tenant_graphs` in `ActiveGrantsForSubject`). Cheap,
  catches the real violation (queries), tolerates the generated-struct noise.
- **Option B (stronger):** split the schema per module for sqlc only — a small generator that
  slices `migrations/` tables by prefix into `internal/<m>/adapters/schema/` inputs. Kills the
  50k duplicated lines and makes cross-module queries a compile error. More moving parts; do it
  only if A proves insufficient.

**Acceptance.** CI fails on a test PR that adds a `person` query touching `oikumenea.tenant_units`;
(Option B) a migration to one module's tables regenerates only that module's package.

### <a id="r-09"></a>R‑09 — `person` is a god module  **[high]**

**Evidence.** `internal/person/` owns: core bio (D-PersonBio/D-PersonNamesCLDR), contacts,
social channels, relationships, citizenships/residences, physical identity + encrypted ethnicity,
addresses, institutional ties, watchlist matches + sanctions, and the M35 overlays (crypto
wallets, personality, political leaning). Sizes: `adapters/queries/person.sql` 1,270 lines →
`person.sql.go` 6,032; `adapters/repository.go` 2,994; `transport/service.go` 1,823;
`application/service.go` 1,532; `domain/person.go` 1,259. Compare: the next-largest domain module
is ~⅓ of this. Ten other modules subscribe to its events; it holds 4 late-bound seams.

**Why it matters.** Every new person-adjacent milestone (M31–M35 all landed here) grows the same
five files; merge conflicts, review blast radius, and the temptation to share repository/tx
helpers across unrelated concerns all scale with it. It is also the module where PII tiers
concentrate — the hardest code to review is in the biggest files.

**Fix sketch.** Split by data sensitivity + change cadence, keeping ONE Conjure service surface
(transport can stay thin and delegate — the API contract need not change):
- `person` (core): identity, names, bio, ranks, read-scope, merge/purge orchestration.
- `personprofile`: contacts, social channels, relationships, addresses, institutional ties.
- `personsensitive`: physical identity/ethnicity, overlays (wallets/personality/political),
  watchlist matches + sanctions — everything envelope-encrypted or `pii:special`, so the crypto
  surface and its reviewers live in one place.
Each gets its own `application`/`adapters`/`queries` package; purge/merge stays orchestrated by
core via the existing event fan-out (the split modules subscribe like external modules already
do). Do it file-move-first (pure `git mv` + package renames), no behavior change, then split the
oversized `person.sql` along the same lines.

**Acceptance.** No file in the three modules exceeds ~800 hand-written lines; `go test ./...`
green with zero query-text changes in the first PR; purge integration test
(`internal/person/overlays_integration_test.go` and friends) unchanged and green.

**Status — DONE (uncommitted, green); D-PersonModuleSplit fully delivered incl. the doc entity-section move.** The
**application-layer** split landed
per [D-PersonModuleSplit](decisions.md#d-personmodulesplit--the-person-god-module-splits-into-core--profile--sensitive-behind-one-personservice):
new `internal/personprofile` + `internal/personsensitive` (+ shared `internal/person/appkit`) behind the
one `PersonService`, with the whole `crypto.Cipher` surface now in `personsensitive`; a **shared**
`domain` kernel + **unified** `adapters`/`queries` keep merge/purge and `GetPerson` working with zero
query-text change; `go build/vet/test ./...` + full integration green. All person-family hand-written
files are < 800 lines **except** `adapters/repository.go` (3003) + `domain/person.go` (1259) — the
data/domain layer, deferred to **PR‑2b**. Docs: [personprofile.md](../modules/personprofile.md) +
[personsensitive.md](../modules/personsensitive.md).

### <a id="r-10"></a>R‑10 — Same-tx event bus is load-bearing everywhere; extraction-readiness is now aspirational  **[medium]**

**Evidence.** `pkg/events/events.go` (synchronous, same-transaction, handlers receive the
publisher's `pgx.Tx`); `cmd/oikumenea/main.go` wires `SubscribePersonEvents` from **ten** modules
(membership, order, authorization, document, education, company, vehicle, finance, religion,
identityfederation). The docs' extraction story ("cross-module mutations are domain events, keeps
the monolith extraction-ready") assumes events could become async; but merge/purge correctness
now *depends* on same-tx atomicity across ten modules' tables, and the outbox seam is explicitly
"a later addition" (package comment).

**Why it matters at target scale.** (a) A person merge/purge is one giant transaction spanning
10+ modules' tables — long lock lists, and every new module widens it. (b) Any real extraction
(or even a second binary sharing the DB) silently breaks the atomicity contract. (c) There is no
at-least-once channel for effects that *should* be async (notifications, projections, cache
invalidation for R‑01's epoch), so everything defaults into the tx.

**Fix sketch.** Not "make it async" — same-tx is the correct semantic for order-apply and
merge re-homing. Instead:
1. **Classify** events in `docs/architecture/patterns.md`: `atomic` (same-tx, current bus) vs
   `notify` (after-commit). Today's events all stay `atomic`.
2. Implement the parked **transactional outbox** for the `notify` class (one table, one poller;
   hermenea's job-queue code is a working template — `internal/hermenea/runtime`), so the next
   async-shaped need (R‑01's epoch bump, webhooks, search-index refresh) doesn't get jammed into
   the write tx by default.
3. Add a guardrail: the bus refuses `Subscribe` after boot (it already assumes this; enforce it)
   and the docs state that adding an `atomic` subscriber is a decision-level change (it widens
   every publisher's transaction).

**Acceptance.** Outbox exists with an integration test (publish-after-commit, crash between
commit and dispatch → redelivered); patterns.md documents the two classes; no behavior change to
existing events.

**Status — DONE (uncommitted, green); D-EventOutbox.** All three parts landed. (1) **Classified** —
[patterns.md](patterns.md) *Domain events: atomic vs. notify* + [decisions.md](decisions.md) D-EventOutbox;
`atomic` stays the default and every event today is `atomic`. (2) **Transactional outbox** — new
`oikumenea.platform_outbox` (migration `0036`; infra, no RLS); producer side `pkg/events.OutboxWriter`
enqueues on the write tx; the `internal/platform/outbox` **dispatcher** drains after commit, claiming
`FOR UPDATE SKIP LOCKED` (replica-safe, mirrors the hermenea worker), backoff + dead-letter, at-least-once
(idempotent handlers). Started in `main.go`, folded into cleanup. **No `notify` producers yet** — a
live-but-empty proven seam. (3) **Guardrail** — `events.Bus.Seal` is called after all subscribers wire;
a later `Subscribe` **panics** (unit-tested), and the docs state an `atomic` subscriber is a
decision-level change. Verified: `internal/platform/outbox/outbox_integration_test.go` (enqueue-on-commit
durability across the commit/dispatch gap → delivery → at-least-once redelivery on handler failure →
dead-letter) + `pkg/events` Seal unit tests; full `go test -tags integration ./...` = **55 packages ok**;
server boots clean (dispatcher started, bus sealed, no seam panic). No behavior change to existing events.

### <a id="r-11"></a>R‑11 — Late-binding setter web in the composition root  **[medium]**

**Evidence.** `cmd/oikumenea/main.go`: `pep.NewUnbound()` → `Bind` inside
`authorization.Register`; `middleware.NewUnbound()` → `authenticator.Bind(...)` near the end;

**Acceptance.** Deleting any `Set*`/`Bind` line makes the server refuse to boot with a message
naming the missing seam; no `== nil` seam guards remain in application code.

**Status — DONE (uncommitted, green).** Every mandatory late-bound holder now exposes

### <a id="r-12"></a>R‑12 — In-request synchronous hermenea call: no deadline, made while holding the pinned connection  **[medium]**

**Evidence.** `cmd/oikumenea/main.go` (~line 282) builds the watchlist client with
`WithMaxRetries(0)` but no `WithHTTPTimeout`; `internal/watchlistclient/client.go` adds none. The
call happens inside a request whose context carries the pinned RLS connection (R‑03). Hermenea in

**Why it matters.** oikumenea's request latency (and a pooled DB connection) is coupled to a

oikumenea (the fate-sharing R‑03 makes global).

**Fix sketch.** `httpclient.WithHTTPTimeout(10 * time.Second)` (hermenea serves cached answers in
ms; a miss that needs >10s should fail into the existing "screening unavailable" error path);

half-open breaker later; the timeout is the load-bearing part.

**Acceptance.** Integration test with a stalling fake hermenea: request fails in ~10s with the
degraded-screening error; concurrent unrelated requests unaffected (pool not exhausted).

survivable at 10⁶ and catastrophic at 10⁷.

Three findings changed the code:

1. **The correlated closure probe was the `unitId` cost.** Expanding the subtree per candidate
   person measured **242 ms**; hoisting it to an uncorrelated `unit_id IN (SELECT … UNION SELECT
   descendants)` — a subquery that reads only the facet parameters, so the planner evaluates it once
   and probes a hash — measured **33 ms**, and held at 38 ms under `plan_cache_mode =
   force_generic_plan` (the generic-plan case R-21 warns about) against 440 ms for the correlated
   form.
2. **`VisiblePersonIDsForSubjectDense` is rewritten to drive from `person_persons`** (the shape
   `…Search` already used), so the facet predicates sit on the driving relation: `unitId` at root
   reach went **816 ms → 30 ms**, and the unfiltered baseline improved from the recorded 39 ms to

   was rewritten to match; the two candidate shapes measured within noise of each other there
   (38 vs 42 ms at mid reach), so consistency decided it — all three visibility queries now have one
   structure and one copy of the facet block, and the `DISTINCT` + sort is gone.
3. **The harness was measuring its own bloat.** The enrichment rewrites every person row several
   times, leaving a 749 MB heap for 10⁶ persons against 150 MB reclaimed. On the bloated table the
   two candidate sparse shapes looked 2× apart; on the clean one they are equivalent. `-enrich` now
   ends with `VACUUM (FULL, ANALYZE)` so this cannot mislead the next measurement.

A fourth finding came from the **live** end-to-end run, not from any test:

4. **The `unitId` facet returned an EMPTY page to an instance admin.** person's own tables carry no
   row security, so the directory list had always read from the bare pool; the facet's predicate
   probes `membership_memberships`, which **is** RLS-protected. On a connection that is not the
   request's pinned one the `app.*` GUCs are unset, so `authz_unit_in_reach` sees neither the
   instance-admin bypass nor any grant, the `EXISTS` matches nothing, and the endpoint answers `200`
   with zero rows to a caller entitled to every one of them — the worst shape of wrong, because it
   reads as "no results" rather than as a fault. Fixed by routing the two list paths through
   `db.RequestQuerier(ctx, s.pool)`, as every other module with RLS-touching reads already does.
   **The integration suite could not have caught this**: it connects as a superuser and so bypasses
   RLS entirely. The regression guard is therefore a source check
   (`internal/person/application/rls_querier_test.go`) at the layer where the mistake is made.

**No index shipped, and none is warranted:** every filtered path is already index-backed, and the
residual cost is scan width and probe count (how many candidate rows a page must walk), which no
index on `person_persons` changes. The M56 stage-board `Migrated` cell stays `➖`.

Honest residuals, recorded rather than smoothed over:
- The scoped unfiltered baseline at mid reach went **19–28 ms → 41–47 ms**. The pre-M56 query was

званнями*) and the pyramid's wing labels through the same enum option labels the filter `<select>`

### M57 ticket 3 follow-up — `levelMin`/`levelMax`, and a fourth non-facet class (2026-07-30)

The one inert chart on the board, closed. M56 declared `unit.level` a `numeric-range` facet but pinned
its arg to the pre-existing scalar `level` via `ArgOverride`, with the range args "additive and
deferred to when the bands are actually consumed". Drawing a band chart is what consumes them: a band
is a RANGE, one value cannot express one, so the bars were readable and dead.

`listUnits` and `unitStats` now ship `levelMin`/`levelMax` (inclusive), the facet binds the derived
pair, and the units-per-level bars link like every other segment. Three things about the shape:

- **The scalar is retained and still honoured**, because the contract is expand-only — removing a
  query arg breaks every stored link and every client that still sends it. The three predicates are
  **ANDed**, so a caller passing both gets the intersection rather than one silently winning
  (asserted: `scalar and range compose`).
- **It is classified, not excused.** `pkg/facet` gains a fourth non-facet class, `superseded`, whose
  check is earned like the other three: the successor named in `Drives` must exist, must be a RANGE
  facet over the same column, must take the same Conjure type, and must NOT itself bind the arg —
  so the class can only ever cover a genuine predecessor, never a filter someone declined to declare.
- **An inverted range is a 400, not an empty page.** `levelMin > levelMax` returning zero rows would
  read as "there are none that deep" rather than "that range is impossible".

**The test is the property, not the plumbing.** `TestUnitStatsLevelBandsAreClickThrough` seeds one
unit per band plus one with no level, then holds every band's BUCKET against the row count that band's
own bar-link returns — the console-side equality the whole facet vocabulary exists to guarantee, at
the one place a chart cannot check itself. Hand-broken (`level <= max` → `level <`), it reports
`band 0-1: bucket counts 2 units, its own filter returns 1 — the bar and the list it links to
disagree` on four bands at once.

**Live** (seed-demo, after backfilling `tenant_units.level` from the closure depth, since the seeder
leaves it NULL): the bars carry `?levelMin=0&levelMax=1` … `?levelMin=8`, and the two populated bands
land on exactly the rows they counted — bucket 4 → 4 rows, bucket 36 → 36 rows, both through the
console and through the API. The chip reads `Level: 2 – 3`, and the filter control became a min/max
pair with no widget change, because arity comes from `params`.

**Fixed en route, and it is the third time this exact bug shape has appeared:** `UnitSelect` and
`NewUnitForm` called the positional `listUnits(org, …, 200)`, and inserting two args in the middle
moved `200` from `pageSize` onto `rootsOnly`. Both call sites now use the generic
`api.request("GET", "/tenant/v1/units", { query })` — a query string names what it means and cannot
shift when the contract widens. (M56 ticket 4 fixed the same call sites when its six facet args
shifted `200` onto `graph`; the comment left behind said "pageSize is the 11th arg", which is exactly
the kind of knowledge that rots.)

### M58 ticket 1 — the audit dashboard, and what a ledger broke (2026-07-31)

`GET /audit/v1/stats/audit` plus the console's `audit` entry: list, dashboard and the four catalogued
charts, over the nine filter args `AuditService.query` has always shipped. The milestone called this
"no contract churn", and its ARGS needed none — but every other assumption the M56/M57 kernel had
quietly made turned out to be about the five operational-core types rather than about facets, and the
value of doing audit first is that all four surfaced at once.

**1. A collection with no RID type token.** `pkg/facet` validates a type against the pkg/rid registry
and admits objects and links; an audit row is an ACTION record whose RID belongs to the producing
service (tenant, person, …), so there is no `audit` triple to register — and inventing one would make
`rid.TokenOf`, whose whole job is to describe real identifiers, describe some that never exist. The
resolution is `ObjectType.Ledger`: a one-field escape carrying its own reason, refused for a token
that IS registered, and held to **at most one** such type by a guard, so a second ledger has to be
argued rather than copied. The kind rule is untouched — an invocation is still not a collection.

**2. An open value set.** `action` has a registry (`pkg/action`, 288 codes) but no CHECK; `target_type`
has neither. Neither is an enum (nothing to zero-fill) nor a ref (no RID to label), so `KindCode`:
ranked top-N, and **the key is its own label**.

**3. Visibility that is not a predicate.** `audit_log` is `FORCE ROW LEVEL SECURITY` with a `unit_id`
reach probe, and the gate is the coarse `audit.read`-anywhere. So the aggregate ships **ONE arm** where
every M57 type ships two: there is no subject to fold in. That is safe for exactly one reason — the
read runs on the request-pinned connection — so the `db` source guard was extended to cover it, and
parameterized over the module's accessor (audit's is `reader`/`RequestDBTX`, because its repository
factory takes a DBTX so an audited write can pass the caller's transaction).

**4. A day-grain axis.** The first `dateTrunc` facet that is not monthly, because an audit trail is
read day by day and a monthly bar hides the spike it is read for. The console gained `daySpan`
(gap-filling, bounded) and `fmtDay`; `since`/`until` are Conjure **datetimes**, so a picked day widens
to that day's RFC-3339 endpoints — one helper serving both the filter control and the histogram's
click-through, because a bar and a typed date that disagreed would be the same bug in two places.

**Two bugs found, both by the LIVE run and neither by any test that existed:**

- **`TopN()` looked only for a ref facet**, so a selection made entirely of code facets bound
  `top_n = 0` and **every bucket collapsed into `(other)`** — not empty, not an error, and completely
  wrong. It is now every top-N *strategy*, with a regression test named after the shape.
- **`facets=` is not "count only".** An EMPTY `facets` means *every facet the caller may read*; a
  list of nothing (`,`) means none. M57's document "expiring soon" tile had been sending `""` and
  quietly fetching the whole dashboard a second time. Fixed, and the two forms are now spelled out
  where the query is built.
- (And a third, cosmetic but wrong in principle: the bucket-label fallback prettied `-` into an en
  dash, which is right for the age band `25-34` and wrong for `service-principal.grant` — a label that
  no longer matched the value its own segment filters by.)

**Verified live** (`oik serve` + `next start` on the seed-demo DB): the ledger dashboard renders in
44–73 ms over 27 entries, `/audit` 307s to `/explore/audit`, the 30-day window arrives as a visible
`since=` chip, and every clicked segment lands on exactly the rows it counted — `action`, `outcome`,
`targetType`, `actorType` and both day buckets, checked against exhaustive paging of the same list
(9/9, 27/27, 9/9, 27/27, 18/18, 9/9; total 27/27). Guards: five new ones, each hand-broken and
confirmed red before being reverted. `TestAuditStatsDayBucketsAreClickThrough` was hand-broken by
switching the aggregate to month grain, and reported both days missing.

**Recorded, not smoothed:** an unfiltered ledger aggregate scans every monthly partition, which is why
the console sends a window rather than the endpoint defaulting one. At seed-demo scale that is
invisible; the number worth taking is that the 30-day window is the console's lever, exactly as the
`facets` CSV is for person.

### M58 ticket 2 — the first verticals, and what a tree broke (2026-07-31)

`external_organization` and `taxon`, chosen as the two cheapest remaining M58 types: flat tables, no
row-level security, most filter args already shipped. The first was the repetition the milestone
predicted. The second was not — a **tree** broke a different kernel assumption from each of ticket 1's
four, and a **raw-pgx module** broke a fifth that had nothing to do with either.

**(a) A distribution that does not partition.** The M57 contract asserts a facet's buckets sum to
`totalCount`. A taxonomy cannot: `subtree` groups over the transitive closure, so a taxon three levels
deep is counted under each of its three ancestors, and `classification` counts effective theism tags,
of which a taxon may hold several. The alternative — group by `parent_id`, filter to an exact parent —
partitions honestly and then **dead-ends**, because after one click every remaining row shares one
parent and the chart collapses to a single bucket. New `Facet.NonPartitioning`, a reason string on the
`Ledger` pattern, exempting **the summation assertion and nothing else**: the property the vocabulary
actually rests on — a bucket's count equals the rows its own filter returns — is untouched and still
checked per bucket. Contained by two guards: the reason must be substantive, and the facet's table
must not be the listed table (a row has one value in its own column, so it *cannot* overlap; an
exemption there is imitation, not need).

**(b) A closure facet has to be confined to the candidate set — found by the differential, not by
reading.** Once a caller has filtered to X's subtree, X's own ancestors are still ancestors of every
remaining row and would otherwise appear as buckets. `parent` is single-valued, so clicking one
**replaces** the anchor and **widens** the result: the bucket said 22, the list returned 55. Joining
the ancestor back to `cand` confines the buckets to taxa strictly inside the current view, where the
count and the click-through cannot disagree. Uniform, not conditional — at the top level every
ancestor is a candidate anyway.

**(c) The kernel assumed a module's SQL is static text.** `sqlparity_test.go` and
`statsparity_test.go` prove list/stats agreement by parsing `adapters/queries/*.sql`. Religion and
externalorg have no such directory — they build SQL at runtime, by a documented per-module choice, as
do vehicle and finance in the remaining tranche. New `pkg/facet/rawpgx_test.go` carries the same
invariant with a different proof: an **AST** check that both paths call ONE shared filter builder (a
comment naming it must not satisfy the guard), plus a single named aggregate const with a branch per
declared facet in both directions. The two sqlc-shaped coverage floors **defer** to it rather than
exempting the types.

**(d) An arg that took a code, a bucket key that is a RID.** `listExternalOrgs(kind)` and
`listTaxa(rank)` predate the vocabulary and took catalog codes; a ref bucket's key is the catalog
row's RID. Both args were **widened** to accept either spelling — the precedent `listTaxa(religion)`
already set — rather than gaining a second arg meaning almost the same thing. `ClassSuperseded` could
not be used: that class is restricted to RANGE kinds.

**Two real bugs, each found by exactly one method and by nothing else.**

1. **`listTaxa` had been silently losing rows since M22.** It ordered by
   `rk.ordinal, t.sort_order, t.code, t.id` and paged on `t.id > cursor` — different orders, so every
   row sorting after the cursor position with a smaller id was dropped from page 2 onward. On the
   seeded taxonomy that lost **16 of 100 taxa**, invisibly, because a short page still looks like a
   page. Found by the M57 differential (`totalCount` vs exhaustive paging) on its first run, which is
   precisely the class of defect that contract exists to catch. Fixed to a keyset on `code`, which is
   unique among active taxa, indexed, stable and human-meaningful, so one column both orders and
   pages.
2. **Every month segment of a datetime facet linked to a 400.** `buckets.ts`'s `dayPatch` widens a
   bucket key to RFC-3339 endpoints when the arg is a Conjure DATETIME; `monthPatch` did not, and had
   never needed to — every earlier month-grain facet takes calendar dates, and audit's datetime facet
   buckets by day, so the two halves had never met. `external_organization.asOf` is the first
   month-grain DATETIME facet. The chart rendered perfectly and every bar was a dead link. Found only
   by clicking one against the running server; now guarded by
   `TestDatetimeFacetsHaveAWidenedBucketInverse`, anchored on the catalog so it demands the branch
   only for a grain some registered datetime facet actually uses.

**Guards (six, each hand-broken and confirmed red):** shared-filter-builder, single-aggregate-const,
aggregate-branch-coverage (both directions), NonPartitioning-is-earned (reason length **and** the
listed-table rule), and the datetime bucket-inverse.

**Verified live** (`oik serve` + `next start` against the dev DB): both dashboards render in 13–200 ms;
**45/45 taxon buckets and 15/15 external-org buckets** land on exactly the rows they counted, checked
against exhaustive paging over real HTTP; the three `asOf` month buckets match their RFC-3339
endpoints; the subtree drill descends **100 -> 55 -> 22 -> 3** (Christianity -> Protestantism ->
Reformed) with every step exact and the descent terminating naturally; and **67/67 chart segments
rendered by the console** navigate to a working filtered list. Browsing moved out of both bespoke
pages while their editors stayed — the taxonomy tree editor, clergy/site/discovery panels, org
create/merge and the kind catalog all still render.

**Not done, and why.** `company` and `institution` remain blocked on a catalog decision: they are
sidecar tables on `tenant_organizations` and have no RID token of their own, while the `Ledger` escape
is capped at one and correctly held by `audit`. Recorded as an open seam in
[facets.md](facets.md#open-seams) with the three candidate shapes, to be argued before either type's
ticket rather than during it.

### M58 ticket 3 — the raw-pgx tranche, and a guard's first real test (2026-08-01)

`vehicle`, `account` and `card`: the two remaining raw-pgx modules, chosen because
`pkg/facet/rawpgx_test.go` — the guard file ticket 2 left behind — had only ever been applied to the

from is a guess. It held without amendment; everything else this ticket cost was somewhere else.

**The kernel took no new exemption.** No `Ledger`, no `NonPartitioning`, no new `Kind`, no new

### M58 ticket 4 — the last two-arm type, and a gate that gates nothing (2026-08-02)

`organization` and `languoid`, chosen because they are the **only two remaining M58 types whose list
endpoint already works unconditionally**. Every other candidate needs a list mode invented first —
`location` has no unfiltered branch, `enrollment` no top-level list at all, `assignment` requires one
of `subjectPersonId`/`targetUnitId` — and each is also unverifiable on the current dev database (0
role assignments; `type_id` NULL on all 40 locations). Facet work on a type you cannot exercise is
the shape of ticket 3's worst defect, so the two that could be exercised went first.

**The finding: `gateUnits` gates organizations, and for an organization it gates nothing.**

`listOrganizations` is shadow-gated by `gateUnits` — the *unit* gate, applied to organization rows.
On a unit that gate is real: `FilterVisibleUnits` probes reach with `ReadableUnitsForSubjectAmong`,
and a shadow unit inside the reach passes. On an organization it is not. That probe's only match arms
test `a.target_unit_id = cand.unit_id`, and `authz_role_assignments.target_unit_id` is
`NOT NULL REFERENCES tenant_units` — **an organization RID can never appear in it.** The reach set for
an org is empty by construction; a shadow organization is visible to an instance admin and to nobody
else, whatever the visibility model reads like.

The tranche table had said organization "needs the full M57 two-arm treatment (rule 3)". **Right about
the shape, wrong about the predicate.** Two arms, yes — but the scoped one is `AND visibility =
'public'`, not unit's `visibility='public' OR id IN (SELECT authz_readable_units(@subject))`. Copying
unit's predicate would compile, pass every guard, and **count exactly the same rows today**; it would
diverge only on the day org reachability is fixed, when the list would still show zero shadow orgs
while the chart showed some — a differential break in the direction nobody looks at. The honest arm
matches what `gateUnits` actually leaves, which is what the contract asks for.

Because that is a claim about *another module's* schema, it is asserted rather than assumed.
`TestOrganizationShadowIsUnreachableForEveryNonAdmin` grants a subject **subtree** read over the
shadow org's own unit — and checks the reach really took, so the test cannot pass by the grant having
done nothing — then shows the org count does not move. It is written to go **red** the day the gap is
closed, which is exactly the day the arm must change. The gap itself is now an
[open seam](facets.md#open-seams), deliberately not fixed here: it is an authorization-plane
read-surface decision with three unargued shapes, not a facet one.

**The first composite code facet.** `macroarea` is set-valued, stored semicolon-joined (183 of 27 177
rows read `Africa;Eurasia`). It is grouped by the **literal string** rather than unnested, and that is
not a shortcut: the filter is an exact match, so each bucket's count equals what its own filter
returns — the property the vocabulary rests on. It therefore **partitions**, needs no
`NonPartitioning`, and could not take one anyway: the kernel refuses that exemption when the facet's
table IS the listed table, since a row has one value in its own column and cannot overlap. Live, 9 of
the 15 top-N buckets are composites and every one was verified against its own filter.

**The first WIRE BREAK the vocabulary has demanded.** `ClassPaging` covers only
`pageSize`/`pageToken`; `listLanguages` shipped `limit` and was the lone holdout among twelve types.
The guard describes a real convention and the endpoint was the outlier, so the **arg was renamed
rather than the guard widened**. Contained: every consumer is in-repo, `hermenea` does not call this
endpoint, and the sole Go consumer uses the *domain* `Filter.Limit`, which keeps its name — the rename
was a contract decision and propagating it inward would have churned connector and dataimport for
nothing. Verified live that `?limit=5` is now genuinely **inert** (falls back to the default 100)
rather than half-honoured.

**Two things that were NOT defects, recorded so they are not re-litigated.**

1. **The pii sweep came back clean — the first time in four tickets.** 0018 and 0019 each found
   faceted columns with no classification; here all seven were classified at creation. The sweep
   still had to be *run*: the guard fails an unclassified column, and an omitted comment must fail
   rather than default. What changed is the answer, not the obligation.
2. **`family_code`'s padding risk is theoretical.** The column is `char(8)`, so the facet emits
   `rtrim(family_code)`. Measured after the fact against the live catalog: **every glottocode is
   exactly 8 characters** (zero padded rows) and the `::text` cast the branch already applies strips
   trailing blanks on its own. The `rtrim` fixes nothing and stays as belt-and-braces — it states the
   intent where the conversion rule would otherwise be load-bearing and invisible. Written down this
   way on purpose: ticket 3 spent a round re-deciding a `vehicle.color` "defect" that was a stale
   claim nobody had measured.

**A LEAK, found by pulling on the finding.** Checking whether a shadow org's existence was already
inferable elsewhere — a fact that bears on how to fix the reach gap — turned up that
`getOrganization` was documented **"(shadow-gated)"** in the contract and applied **no gate at all**.
`listOrganizations` trimmed shadow organizations for a non-admin; the point read on the same object
handed them over to anyone holding `organization.read`. Demonstrated live before the fix: the list
returned 3 rows with the shadow org absent, and `GET /organizations/{that RID}` returned **200** with
its code, visibility and state.

Two surfaces on one object disagreeing about visibility is the shape that makes a leak invisible —
each looks correct read on its own, and the contract line that should have caught it was the thing
asserting the false claim. Fixed with **`gateUnits`, the same helper the list uses**, deliberately
rather than an inlined visibility check: the rule now has one implementation, so when the reach gap
is closed both surfaces move together instead of one being remembered. A gated-out organization is
`OrganizationNotFound`, **not** a permission error — `shadow` hides *existence*, and a 403 would
confirm the RID names a real organization, which is exactly what the list refuses to say by omitting
the row. Verified live that the gated read and a genuine miss are byte-indistinguishable apart from
the caller's own echoed RID.

**The first guard written for it was useless, and hand-breaking is what showed that.** The obvious
regression test — point read and list agree for every organization — was written at the *application*
layer, where the tenant integration suite lives. Reintroducing the leak left it **green**: the gate
is applied per handler in the TRANSPORT, and an application-layer test has no handler to lose it
from. The guard that works is `transport/shadowgate_test.go`, which inspects the handlers themselves
and asserts each shadow-bearing read routes through `gateUnits`; both breaks — dropping the gate, and
inlining the rule instead of using the shared helper — go red. The application-layer test stayed, with
its comment corrected to say what it does and does not cover.

The structural form (does it call the one helper?) was chosen over a behavioural one (does a shadow
org 404?) for the same reason the arm predicate was: organization reachability is empty by
construction today, so a behavioural assertion written against today's answers would need rewriting
the moment that is fixed — precisely when a guard is least likely to be re-derived correctly. A
companion check keeps the presence test honest by refusing any *other* handler that compares against
`VisibilityShadow` on its own, so "calls `gateUnits`" cannot quietly stop meaning "applies the rule".

**One real defect, in the seeder.** `seed-demo` creates every org with the column defaults, so
`visibility` and `state` would each have been a single bar — ticket 3's "a chart that renders and
proves nothing" in its other form. Worse, the fix could not be *applied*: the seeder short-circuits
on existing demo data and `-reset` is blocked on any dev database carrying hand-made rows it does not
own. So the short-circuit now refreshes the idempotent spreads before exiting, and the seeder stopped
being all-or-nothing. The same gap showed up in the *test* fixture — every languoid there has a NULL
macroarea — so the language integration test seeds a spread including a composite rather than letting
that facet go unchecked.

**`domain` collapses its top-N tail in SQL; `UnitStats`' ref branches do not.** The kernel's
`topNBuckets` orders and appends the synthetic buckets but never truncates, so a facet declaring
`TopN 15` whose SQL emits every group renders more bars than it promised. Unit's branches get away
with it because its ref cardinality is a handful of catalog rows; the domain catalog is

### M58 ticket 4 follow-up — organization reach, derived (2026-08-02)

The open seam ticket 4 recorded is closed, and the way it closed is the argument for how it was
written down. Of the three shapes on the table — a nullable `target_org_id`, an org-level `scope`, or
deriving org reach from unit reach — the third was chosen: **an organization is visible when any of
its live units is in the subject's reach.**

*Why derivation.* The other two add a primitive to the PDP for a question unit reach already answers.
Derivation also **discloses nothing new**, which is what makes it cheap rather than merely small:
`listUnits` takes the org RID as a REQUIRED argument and gates the *units*, not the organization, so
a subject with reach inside an org could already enumerate its units and was already holding its RID.
The organization simply did not say so. And it is **precise** — verified live, a subject with reach
into `privatbank` sees that organization and still 404s on `upc-parish`, the other shadow org.

*What it cost, and what it did not.* `ReadableOrgsForSubjectAmong` + `FilterVisibleOrgs` + a `gateOrgs`
sibling in tenant's transport, and the same derivation folded into `OrganizationStatsForSubject`. **No
migration**: the probe joins `tenant_units` by `org_id`, and `tenant_units_org_idx (org_id) WHERE
deleted_at IS NULL` already exists and matches the predicate exactly. Scoped dashboard 8 ms → 22 ms.

`gateOrgs` is a **sibling** of `gateUnits`, not a call into it with a flag. That is deliberate: the
two ask different questions, and a shared entry point taking a mode is precisely what let an
organization RID be handed to the unit reach probe unnoticed for eighteen milestones.

**Three guards behaved as designed, which is most of the point.**

1. `TestOrganizationShadowIsUnreachableForEveryNonAdmin` **went red**, carrying the message it had
   been written to carry for this day ("if that is now correct, organizations became reachable and
   … must be replaced with a reach predicate"). A guard that pins a fact you expect to change is
   worth writing when it tells the next person what to do about it. Replaced by
   `TestOrganizationReachIsDerivedFromUnitReach`, which asserts **both** directions from one setup —
   either alone is satisfiable by a bug ("sees it with reach" passes if the gate stopped gating,
   "does not see it without" passes if reach went back to empty).
2. `shadowgate_test.go` **survived unchanged in structure**, because it was written structurally
   ("does this handler call the helper that owns its rule?") rather than behaviourally. Only the
   expected helper per handler moved. It also gained a check naming an org handler calling
   `gateUnits` as the *original bug* rather than the wrong helper.
3. The **application-layer** org test stayed green throughout and correctly so — it cannot see a
   transport gate, which is the lesson from the previous commit, and the live HTTP check is what
   covers the boundary.

**Verified live** (admin, an outsider with reach into a public org only, and an insider with reach
into a shadow org's unit — the same subject moved, so nothing else varies):

| Subject | stats total | `shadow` bucket | list rows | `GET` reached shadow org | `GET` other shadow org |
|---|---|---|---|---|---|
| admin | 5 | 2 | 5 | 200 | 200 |
| insider (reach into `privatbank`) | 4 | 1 | 4 | **200** | **404** |
| outsider (reach into a public org) | 3 | 0 | 3 | 404 | 404 |

Chart and list agree at every row.

### M58 ticket 5 — the sidecar profiles, and a list that never gated (2026-08-03)

`company` and `institution` — the last two M58 types whose list endpoint already worked
unconditionally, and the two the ticket-2 survey recorded as **blocked on a catalog decision**.

**The catalog decision: a `Profile` arm, the sibling of `Ledger`.** `company_org_profiles` and
`education_org_profiles` are sidecars PK'd to `tenant_organizations` (M41 / D-UnifiedOrgGraph), so
their rows' RID token is `organization` and `facet.Register` refused them. `Ledger` could not absorb
them — it is capped at one, `audit` holds it correctly, and these rows *do* have a token; it just is
not theirs alone. `Profile` names the token the rows are keyed BY.

Two things make it a different kind of escape from the one it sits beside. It is **uncapped**,
because a sidecar-on-organization is a pattern rather than an exception. And it is **checkable**: a
ledger's "these rows have no token" is written down nowhere and has to be argued, while a profile's
"these rows are keyed by that token" is a fact the DDL records — so the guard parses the migrations
and asserts the profile table's primary key `REFERENCES` the profiled token's table. That is what
replaces the cap. A companion guard pins that every profile hangs off the *same* parent today, which
is not hypothetical: `religion_org_profiles` is the same shape keyed to `tenant_units`, so the day a
religion profile becomes listable the guard asks for the modelling argument instead of accepting the
copy.

The two rejected shapes are recorded rather than dropped. A **domain-discriminated `organization`**
would bind the facets to `listOrganizations`, which selects no sidecar column — so the endpoints that
actually serve these rows would stay unfilterable and their console pages would stay bespoke. **New
RID types for the profiles** gives the cleanest routing and costs a migration re-keying two sidecars
and every table that references `institution_id` as an org RID, against D-UnifiedOrgGraph's "a
company IS a tenant organization".

**And a LEAK, on three surfaces.** `listCompanies` and `listInstitutions` applied **no visibility
gate at all** — since M21 and M20. Both join `tenant_organizations` and never looked at `visibility`,
so a caller holding `company.read` / `education.read` was handed the shadow organizations
`listOrganizations` trims. It is the `getOrganization` leak of ticket 4 in a worse form: a whole list
rather than one RID at a time, in the two modules that inherited its rows. The point reads leaked the
same rows one at a time, and unified **search** was a third door — both types were registered under
`scope.NewCatalogScope()`, the identity trim.

All three now route through one helper per module over the `pep.FilterVisibleOrgs` the ticket-4
follow-up built, plus a new `scope.NewOrgScope` for search. A gated-out row is `NotFound`, **never a
403**: `shadow` hides existence, and a permission error confirms the RID names something real. The
dashboards fold the predicate into SQL rather than trimming the result, because trimming after the
fact is right for a page and wrong for a count.

**The search door had no guard, and breaking it is what showed that.** Of the seven breaks attempted,
six went red immediately; reverting the search providers to the catalog scope left the entire suite
**green**. The per-module `transport/shadowgate_test.go` files cannot see it — search bypasses the
transport and calls the application service, and the scope that replaces the gate is a field in a
composition-root literal. `cmd/oikumenea/searchscope_test.go` now asserts, by AST, which scope each
provider is registered with, and refuses a NEW provider that is not in its list — so `catalog` has to
be *chosen* rather than inherited from whichever line it was copied from.

**FOUR aggregate arms per type**, the `person` shape rather than `organization`'s two: a profile has
BOTH a visibility gate (it IS a tenant organization) and an R-21 search twin, so the square is
`{plain, search} × {admin, scoped}`. The scoped arms carry the **derived** org reach; copying unit's
own `id IN (readable_units)` would compile and match nothing, since an organization RID can never
appear in a readable-UNIT set.

**`industryClass` could have taken `NonPartitioning` and does not.** `company_industry_assignments`
is M:N, so the exemption was available and legitimately earned — the facet's table is not the listed
table, which is exactly what the guard allows. Confining it to the **primary** assignment partitions
honestly *and* answers the question the chart is read for. Ticket 3's `registrationCountry` reasoning,
and the rule it stated: an exemption being available is not a reason to take it. Pinned by
`TestCompanyIndustryFacetCountsOnlyThePrimary`, which gives one company a primary and two secondaries
and asserts it is counted once.

**`foundedOn` is the first YEAR-grain facet, and the live run is what taught it its limit.** The grain
is what the data demands: foundings span more than a century, where a month histogram would be ~1500
buckets of which almost all are zero. The console gained `yearSpan` + a `yearPatch` inverse — and the
inverse shipped with the datetime-widening branch its *month* sibling lacked for two tickets, because
that omission is precisely the bug ticket 2 found (every month segment of a datetime facet linked to
a 400; the chart rendered perfectly and every bar was dead).

Then the live console rendered **356 bars for 8 institutions**. `yearSpan` densified 1661–2016 the
way `monthSpan` densifies a fiscal year, and every one of those 348 empty bars was a live link. The
dense axis exists to make a **gap** visible, and past a screenful it shows nothing but gaps; a month
histogram covers an operational window and cannot do this, while a founding histogram covers however
long the institution has existed. So `yearSpan` gives up past 60 years — the same visual budget the
widest shipping chart already uses (the ~54-bar vehicle fleet age) — and returns the populated years.
What is lost is the visibility of gaps at a width where nobody was reading them; what is kept is every
property the vocabulary depends on. **356 → 15 segments**, found by rendering it and by nothing else.

**Three stale claims from ticket 4's follow-up, corrected.** Deriving organization reach changed the
behaviour and left three descriptions of the old rule behind: `listOrganizations`' Conjure docs
("because no role assignment can reach an organization"), `organizationStats`' docs and its
`OrganizationStats` DTO, and the header comment of `orgstats_integration_test.go`, which still
described the deleted `TestOrganizationShadowIsUnreachableForEveryNonAdmin`. That is the same defect
class the ticket is about — a contract asserting a gate that is not what runs — so they are fixed
here rather than noted.

**One real defect in the seeder, and a rule that stopped being deterministic.** Phase A creates
exactly one company and one university, so five of the ten charts would have had a single `(unknown)`
bucket — ticket 3's finding in the module that inherited it. `seedProfileSpread` adds nine companies
and seven institutions, create-if-absent by code, and runs from the **refresh** path too, widening it
from "re-apply the spreads" to "re-apply the spreads and add what a later ticket needs". Separately,
`spreadOrgFacets`' positional rule ("shadow from the 4th code onward, ordered by code") was right for
five orgs and became wrong the moment sixteen more existed — it would have marked nineteen of
twenty-one shadow, silently. Replaced with explicit codes: a rule whose meaning depends on how many
rows happen to exist is not deterministic in the sense that matters.

**The pii sweep came back dirty again.** Ticket 4's came back clean and recorded that "the obligation
stands, only the answer changed"; the answer changed back. Both sidecars classified their identifying

thinks of as bookkeeping. Migration 0021 classifies six columns and adds five indexes.
