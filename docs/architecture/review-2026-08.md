## Findings

### <a id="r-20"></a>R‑20 — Zero application metrics; the system is fast but blind  **[medium]**

**Resolved (2026-07-10, Phase 9).** A thin metric surface now rides the four hot seams, read via
`metrics.FromContext(ctx)` (no constructor plumbing — the ctx fallback is the same
`DefaultMetricsRegistry` witchcraft emits from): grant cache (`authz.grantcache.hits|misses|revalidations|resets`
+ `.entries` gauge), outbox (`outbox.dispatched|retried|dead` + `outbox.pending`/`outbox.oldest_pending_age_seconds`
gauges, and a **distinct dead-letter WARN** at the `status='dead'` transition), dataimport
(`dataimport.chunk_seconds` + `dataimport.rows.merged|skipped`, tagged `object_type`, at the one central
handler call), and closure edits (`tenant.closure.edit_seconds`, tagged `op`; the slice-row histogram
was **deferred** — the repo's Extend/Shrink methods return only `error`, so latency is the proxy).
`docs/modules/platform.md` gains an **Application metrics & alarm signals** table. Tests:
`TestGrantCacheMetrics`, `TestOutboxDeadLetterEmitsCounterAndWarn`, `TestRecordBacklogReportsPendingDepth`.

**Evidence.** No file under `internal/`, `pkg/`, or `cmd/` registers or emits a single
application metric (`grep -rn "metric1\|metrics.Registry" internal/ pkg/ cmd/` → no registration
call sites; witchcraft's built-in `metric.1` request metrics are all a deployment gets).
Specifically invisible:
- `internal/authorization/application/grantcache.go` — hit/miss/revalidate/reset counts of the
  cache the entire request path now leans on (D-AuthzGrantCache). A TTL misconfiguration or an
  epoch-bump storm would look like "the DB got slow", with nothing to alarm on.
- `internal/platform/outbox/dispatcher.go` — queue depth, oldest-pending age, and **dead-letter
  count**: a `notify` event that exhausts `max_attempts` is set to `status='dead'` and then
  *nothing ever surfaces it* (no log line distinct from the retry warn, no counter, no ops query
  documented). When the first real notify producer lands (R‑13's multi-replica posture rides on
  this seam), silent dead-letters become silent data-flow loss.
- `internal/dataimport` / `internal/hermenea` — chunk apply latency, rows merged/skipped, resume
  events, connector failures. The 1M-record M49 run measured these with ad-hoc test
  instrumentation; production runs of the same pipeline report nothing.
- `internal/tenant` closure maintenance — slice sizes and edit latency (the M48 property: cost ∝
  slice, not graph — unverifiable in a live deployment).
- `audit_log` partition/retention posture — `audit.retention-months` is recorded in config
  (`internal/platform/config/config.go` `RetentionMonths`) but nothing reports "partitions older
  than the intended window exist", so the deliberate operator-act model (D-AuditRetention) has no
  reminder signal.

**Why it matters at target scale.** Every July fix converted a visible failure (slow requests)
into a fast path guarded by machinery with *new* failure modes (stale cache, stuck outbox,
stalled import, bloating audit partitions). At national scale with an operator who is not the
developer, the absence of a metrics surface means the first sign of any of these is a user-facing
incident. The review process itself demonstrated the gap: every acceptance criterion in July
needed custom test-only tracers (`db.WithQueryCounter`) because no production signal exists.

**Fix sketch.** Not a monitoring platform — one thin, deliberate surface:
1. Use the metrics registry witchcraft already ships (`witchcraft-go-server` exposes a
   `metrics.Registry` on the server context; the `metric.1` emitter is already wired) — no new
   dependency.
2. Instrument the four hot seams: grant cache (hits/misses/revalidations/resets + entry count),
   outbox (pending gauge, oldest-pending-age gauge, dispatched/retried/dead counters), dataimport
   (per-object-type chunk latency histogram + merged/skipped counters), closure edits (slice-size
   + latency histogram). Add a dead-letter WARN log with a distinct message on the `status='dead'`
   transition.
3. Document the alarm-worthy signals in `docs/modules/platform.md` (dead > 0; oldest-pending age
   > n×PollInterval; cache hit rate < ~90% steady-state; audit partitions older than
   `retention-months`).

**Acceptance.** An integration test drives each seam and asserts the counters move (the outbox
test forces a dead-letter and sees the counter + distinct log); a compose run shows the metrics in
the `metric.1` log; platform.md lists the signals and thresholds.

### <a id="r-21"></a>R‑21 — The R‑06 search fix wasn't generalized: five surfaces still scan  **[medium]**

**Evidence.** July's R‑06 gave `person_persons` a trigram GIN + SQL-side scoped search
(D-PersonSearch). The same per-keystroke, leading-wildcard pattern survives everywhere else:
- `internal/language/adapters/queries/language.sql` — `ListLanguoids`:
  `l.name ILIKE '%' || q || '%'` over `language_languoids` — **27,177 rows seeded at first boot
  by pinax on every instance** (the one table guaranteed to be big on day one). Backs the
  `LanguagePicker` server-query typeahead.
- `internal/geo/adapters/queries/location.sql` — `SearchLocationsByText`: **six** OR-joined
  `ILIKE '%q%'` columns (locality, admin areas, street, mgrs, raw_address) over
  `location_locations`, which grows with every M32 person address and any gazetteer-fed location
  use; and both it and the spatial queries (`ListLocationsNear`, `ListLocationsInBbox`) paginate
  with `LIMIT … OFFSET` — the only OFFSET pagination left in the codebase (everything else is
  keyset), so deep pages re-scan and rows shift under concurrent inserts.
- `internal/education/adapters/queries/education.sql` — `ListInstitutions` (`code`/`name` ILIKE).
- `internal/education/adapters/queries/education_reference.sql` — `ListPublications`,
  `ListScholarships` (same pattern).
- `internal/company/adapters/queries/company.sql` — `ListCompanies`
  (`code`/`name`/`short_name` ILIKE across a join).

**Why it matters at target scale.** Identical mechanics to July's R‑06: an unanchored `ILIKE`
disables every btree index, so each surface is a sequential scan per keystroke. Language is
already at 27k rows on a fresh install; locations and companies are the tables national-scale
registries and the M30 Wikidata connector feed. The typeahead pattern multiplies the cost by
keystrokes × concurrent users.

**Fix sketch.** Generalize D-PersonSearch instead of re-deriving it per module:
1. `pg_trgm` is already enabled (migration `20260601000005_person.sql`). Per surface: a GIN
   trigram index — languoids on `name` (code lookups already hit the `code` btree via the
   anchored `code ILIKE q || '%'` branch), locations on a generated concatenated `search_text`
   like person's (6 columns → one haystack), institutions/companies/publications/scholarships on
   `name` (+`short_name` via the same generated-column trick where multi-column).
2. Replace geo's `OFFSET` with keyset on `id` (the queries already `ORDER BY id`; the cursor
   machinery exists in every other module).
3. Measure before splitting indexes per column — one generated-column index per table is the
   default; per-column only if EXPLAIN demands it.

**Acceptance.** `EXPLAIN (ANALYZE)` on seeded tables (27k languoids real; 10⁵ synthetic locations
/ companies) shows bitmap index scans for a 3-char query on every surface; no `OFFSET` remains in
`internal/*/adapters/queries/`; existing list/typeahead integration tests green.

### <a id="r-22"></a>R‑22 — Envelope encryption: local-dev-only key backend, no rotation path  **[medium]**

**Evidence.**
- `pkg/crypto/` contains exactly `crypto.go` + `localdev.go`: the `KeyProvider` seam
  (D-CryptoProvider) has **one** implementation — a static KEK decoded from base64 install
  config (`crypto.go` ~line 563: provider selection `case "local-dev":` is the only arm, and the
  default). Every production deployment holding IBANs, PANs, ethnicity, political leaning,
  personality profiles runs on it.
- `crypto.go` ~line 40: `KeyRef` is persisted with every ciphertext "so a later rotation/rewrap
  knows which key wrapped it" — but `grep -rn "rewrap\|Rewrap" pkg/ internal/ cmd/` finds **no
  rewrap code path, CLI, or plan**. The plumbing anticipates rotation; nothing can execute one.
- The blind-index HMAC key (`NewCipher`) has the same posture: static, from install config, no
  re-index path.

**Why it matters.** This is the operational half of the carried R‑14: whatever D-DataScope
decides, the data that stays encrypted is only as protected as a KEK that (a) sits base64-encoded
in install config on every host, and (b) **cannot be rotated** — a suspected KEK leak today has
no remediation short of hand-written SQL + custom code against live tables. Envelope encryption
was chosen precisely so rotation would be cheap (rewrap the wrapped DEKs; never touch payload
ciphertext) — that dividend is unclaimed. For PANs specifically, PCI-DSS Req 3.6 mandates
documented key-management including rotation; the current answer is "impossible", which forces
R‑14's PAN decision toward truncation regardless of product preference.

**Fix sketch.**
1. `oikumenea rewrap` CLI (sibling of the existing `seed` / `recover-admin` commands): walk every
   envelope-encrypted table by `key_ref`, unwrap each DEK with the old provider, wrap with the
   new, update `key_ref` — batched, resumable (the M49 cursor pattern), payload untouched. The
   table list is greppable (`key_ref` columns) and small (~8 tables).
2. A second `KeyProvider` for real deployments — file-based KEK with version suffix is enough as
   a first step (rotation = new key file + rewrap); a cloud-KMS provider can come later behind
   the same seam. Record the provider policy + rotation runbook as a D-CryptoProvider amendment
   in decisions.md and in `docs/architecture/upgrade-safety.md`'s operator guarantees.
3. Blind-index key rotation is harder (values must be re-derived from plaintext, so it needs a
   decrypt-recompute pass) — fold its (rarer) runbook into the same CLI as an explicit flag.

**Acceptance.** e2e in dev: seal N rows under key A, run `rewrap` to key B mid-write-load, all
rows decrypt, `key_ref` counts show 0 remaining on A, kill −9 mid-run resumes; decisions.md
records the provider/rotation policy.

### <a id="r-13"></a>R‑13 — Multi-replica story: the `notify`/scale-out remainder  **[medium, carried]**

**What already landed (July, verified).** Advisory-locked boot seeding (`db.LockBootSeed`; one
seed pass proven under `--scale app=2`), hermenea `worker.concurrency` (4-way SKIP LOCKED
parallelism proven), idempotent-per-window scheduler enqueue
(`cron:<source>:<window>` + `ON CONFLICT DO NOTHING`), and the outbox dispatcher claiming
`FOR UPDATE SKIP LOCKED` (replica-safe by construction, like the hermenea worker).

**What remains open.**
1. **The multi-replica `notify` posture is designed but unproven**: no compose run has ever
   executed two oikumenea replicas *dispatching from the same outbox* (the dispatcher's
   SKIP LOCKED claim is replica-safe on paper; the at-least-once/no-starvation behavior under two
   pollers has no test). The grant cache's cross-replica convergence is integration-tested at the
   epoch level but not in a real two-process run.
2. **No two-replica compose verification** beyond the M49 fresh-boot seed race
   (`docker-compose.scale.yml` un-publishes host ports for `--scale app=2` boot; nothing exercises
   steady-state traffic, cache convergence, or outbox sharing across replicas).
3. **`overview.md` has no multi-replica posture section**: what is replica-safe (stateless
   handlers, SKIP LOCKED consumers, advisory-locked boot), what is per-process (grant cache with
   ≤2 s convergence; outbox poll timing), and what the operator must know (session-affinity not
   required; scale hermenea and oikumenea independently).

**Fix sketch.** One compose scenario (`--scale app=2` + traffic): assert single seed pass
(already proven), grant revoke on replica A enforced on replica B within TTL, outbox events
enqueued via both replicas each dispatched exactly-once-observably (idempotent handler counts),
kill −9 of one replica mid-dispatch redelivers on the survivor. Then write the `overview.md`
section from what the run proved. (R‑20's outbox metrics make the assertions observable — do
R‑20 first or together.)

**Acceptance.** The compose scenario passes and is repeatable (env-gated like `OIKUMENEA_LANG_E2E`);
`overview.md` documents the posture; this finding closes.

### <a id="r-14"></a>R‑14 — Product-scope creep with concrete compliance liabilities  **[medium, decision-level, carried]**

Carried unchanged from [review-2026-07](review-2026-07.md#r-14); still fully reproduces as of
2026-07-09. Needs the user, not an agent.

**Evidence.** The stated identity (CLAUDE.md, `overview.md`) is "a generic personnel &
authorization service (Keycloak-like)". The schema also holds: envelope-encrypted **payment card
PANs** (`migrations/20260601000034_finance.sql`, D-Finance), IBANs, crypto wallets, **inferred**
political leaning (M35, `pii:special`), self-declared ethnicity, religious affiliation,
watchlist/sanctions matches. That is an intelligence/registry platform's data surface.

**Why it matters architecturally (not a moral judgment — the user owns product scope).**
1. **PAN storage puts every deployment in PCI-DSS CDE scope.** Envelope encryption does not
   de-scope: the whole Postgres, the oikumenea binary, its host, and arguably the operator's
   network segment become auditable CDE. If there is no real "recover the full PAN" requirement,
   store issuer BIN + last4 + a blind index — D-Finance already built the blind-index machinery,
   so this is a column diet, not a redesign. (New this cycle: R‑22 shows key rotation is currently
   impossible, which PCI Req 3.6 requires — strengthening the truncation recommendation.)
2. **Inferred special-category data** (political leaning) has a materially different GDPR posture
   than declared data; the code isolates it well (encrypted, one-active, crypto-erased, never
   merged with declared party). The residual risk is *aggregation*: one `person` read surface can
   join ethnicity + religion + politics + finances + location. An access-tier gap here is a
   catastrophic breach — which is why the R‑09 `personsensitive` split and per-module permission
   codes matter beyond hygiene.
3. The identity drift belongs in the docs: either re-state the product ("personnel directory +
   registry platform") or record a boundary decision for what data classes are in/out.

**Fix sketch.** A `D-DataScope` decision block: what the instance is allowed to hold, PAN policy
(truncation+blind-index recommended unless a requirement is named), and a check that every
`pii:special` surface sits behind its own permission code (verify in the person-family transport:
if a single read permission unlocks the whole aggregation surface, split the codes).

**Acceptance.** Decision recorded; PAN either justified in the decision or migrated to
truncated+blind-index form (expand/contract); overlay/sensitive reads verified to sit behind
distinct permission codes.

### <a id="r-24"></a>R‑24 — Person purge/merge atomic fan-out: 12 modules, no width budget  **[low]**

**Evidence.** `cmd/oikumenea/main.go` wires **18** `SubscribePersonEvents`/`SubscribePersonPurge`
calls across ~12 modules (membership, order, authorization, document, education, company, vehicle,
finance, religion, identityfederation, personprofile, personsensitive) — all `atomic`-class, i.e.
inside the one purge/merge transaction. D-EventOutbox correctly made "adding an `atomic`
subscriber" a decision-level change, and the semantics are right (PII erasure must be atomic with
the purge). But nothing *measures* the width: no test or bench records purge latency / lock count
as modules accrue, so the documented decision gate has no signal behind it — M31–M45 each added
subscribers without any number moving.

**Why it matters.** A person purge at national scale locks rows across ~30+ tables in one
transaction. The failure mode is not correctness (it's tested) but tail latency and deadlock
surface growing invisibly, one milestone at a time — exactly the pattern the July review existed
to catch early.

**Fix sketch.** Small: extend the existing purge integration test with the query-counter tracer
(`db.WithQueryCounter`) to record statements + wall per purge, and assert a generous budget
(fails only on step-change regressions, e.g. >2× the recorded baseline). Note the current number
in `patterns.md` next to the atomic/notify classification so the decision gate has a baseline.

**Acceptance.** Purge test records and asserts the budget; patterns.md states the current width
and the budget rationale.

### <a id="r-25"></a>R‑25 — hermenea has no boot-time schema-version gate  **[low]**

**Resolved (2026-07-10, Phase 9).** hermenea now mirrors oikumenea's R‑15 gate, self-contained on the
hermenea side: `migrations/hermenea/embed.go` (`//go:embed *.sql`), a new marker migration
`0006_schema_version.sql` (`hermenea.schema_version`, bumped by future migrations), and
`internal/hermenea/db/schemaversion.go` (`ExpectedSchemaRevision` derived from the embedded bodies +
`ReadSchemaRevision`). `cmd/hermenea/main.go`'s InitFunc fails closed on mismatch/absence, naming
expected vs found + the `atlas migrate apply --env hermenea` remedy. e2e-proven: a DB migrated only
through 0005 aborts boot; a fully-migrated DB and a remediated DB boot OK. Adding a hermenea migration
needs no Go change (`TestExpectedSchemaRevisionDerivedFromEmbed`).

**Evidence.** oikumenea derives `ExpectedSchemaRevision` from its embedded `migrations/atlas.sum`
and refuses to serve against a stale schema (`internal/platform/db/schemaversion.go`, July R‑15).
hermenea has no equivalent: `internal/hermenea/db/` contains only `pool.go` — no schema-version
check of any kind against `migrations/hermenea/` (July's R‑15 fix explicitly said "the hermenea
binary should do the same if it has an equivalent gate"; it has none at all).

**Why it matters.** A hermenea binary deployed against an un-migrated hermenea DB (e.g. the M49
`0005_resume_cursor` columns missing) fails at first job claim with a raw SQL error mid-run,
not at boot with a clear message — the exact footgun class R‑15 eliminated on the oikumenea side,
on the binary whose job is long unattended runs.

**Fix sketch.** Mirror the oikumenea mechanism: embed `migrations/hermenea/`, derive the expected
revision from the last entry, check a `hermenea.schema_version` row (add the tiny table in the
next hermenea migration; write it from the migrate step like oikumenea's) at pool init,
fail-closed with the same style of error.

**Acceptance.** hermenea refuses to boot against a DB missing the latest hermenea migration,
naming expected vs found; adding a hermenea migration requires no Go change.

### <a id="r-23"></a>R‑23 — Prod and dev compose share the `oik-pgdata` volume name  **[low]**

**Evidence.** `docker-compose.yml` (~line 31) and `docker-compose.dev.yml` (~line 42) both mount
`oik-pgdata:/var/lib/postgresql/data` and declare the volume under the same name. Run from the
same directory without `-p`, both compose files resolve to the **same** named volume — so a prod
`up` after a dev `up` inherits dev's initialized cluster and its password, and Postgres skips
init. This exact collision was hit during M16 verification (noted in the compose gotchas) and the
files still carry it.

**Why it matters.** It's a data-integrity footgun on the operator's first real deployment from a
dev machine — worst case, a "prod" stack silently running on a dev data directory.

**Fix sketch.** Rename the prod volume (`oik-pgdata-prod`) — or give the files distinct default
project names via `name:` — and add one line to the deploy docs. Nothing else changes.

**Acceptance.** Fresh `docker compose -f docker-compose.yml up` after a prior dev `up` in the
same directory initializes its own cluster; both stacks list distinct volumes in `docker volume ls`.

### <a id="r-19"></a>R‑19 — D-i18n "all locales in every response" is uncapped  **[low, decision challenge, carried]**

Carried unchanged from [review-2026-07](review-2026-07.md#r-19); needs the user.

**Evidence.** D-i18n (decisions.md) + `LabelsByID` (`internal/localization/application/service.go`)
return a `locale → text` map for every translatable label in every response; supported locales are
admin-extensible (4 seeded since M45: `ukr`/`eng`/`spa`/`por`).

**Why it eventually matters.** Response size for list endpoints scales ×|locales| on every
translatable field. At 4 locales it's noise; an admin adding 20 locales multiplies every catalog
response ~5× with no cap. Record the boundary now: either a documented soft cap on supported
locales, or an optional `locales=` projection query param (explicitly *not* Accept-Language
negotiation, preserving the decision's intent). Also (still true as of 2026-07-09): `LabelsByID`
calls `DefaultLocale` per invocation — worth a small cache when touching this code.

**Acceptance.** The boundary is recorded in decisions.md (cap or projection param); if the
projection param is chosen, one catalog endpoint demonstrates it end-to-end.

(risk removed ÷ effort) and dependency; size each as a milestone in the existing pipeline.
