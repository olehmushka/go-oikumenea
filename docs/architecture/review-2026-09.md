**Stance on binding decisions:** `decisions.md` and `ontology-mapping.md` were treated as
challengeable. R‑31 explicitly challenges a **ratified divergence**
([ontology-mapping.md §4.1](../ontology-mapping.md)); its fix must land as a decision amendment,
not code alone.

**Overall verdict.** The ontology is **real at the schema layer and missing at the API layer**.
What Palantir would call the ontology's *backing datasources* is genuinely strong here — arguably
stronger than it needs to be: every entity is declared Object/Link/Action at design time
(D-Ontology), every row carries a self-describing packed-UUIDv8 RID whose bytes encode
service/kind/type with a per-table `rid_shape` CHECK, load-bearing relationships are reified link
tables on one consistent shape (derived joins deliberately excluded), mutations land in an
append-only partitioned action ledger, the order module (наказ) is a textbook typed
action-with-effects, hermenea is a real pipelines analog, and the PDP core is generic over the
unit DAG. That discipline is *why* the web console could build a universal object view, a ⌘K
palette, and a graph explorer at all. But every one of those generic capabilities is realized
**client-side, against a 1,247-line hand-maintained TypeScript registry** — the backend offers no
cross-type search, no "links for this RID" traversal, no action-type catalog, no object history,
and no type-generic visibility trim. The four hand-synced ontology mirrors have already drifted
(the console cannot decode RIDs from four newer services), and the one guard written to prevent
that (`rid.AssertMatches`) is dead code that both its own comment and `conventions.md` claim runs
at boot. In Palantir terms: the datasources and the type system meet the bar; the **ontology
service on top of them does not exist yet** — and the findings below are, in effect, its
specification.

## Findings

### <a id="r-26"></a>R‑26 — No unified object search; the ⌘K palette fakes it over the first 100 rows per type  **[high]**

> **RESOLVED — Phase 14 (2026-07-13).** `api/search.conjure.yml` → `SearchService.searchObjects`
> (`/search/v1/objects`), implemented as the sketched fan-in: a new thin `internal/search` module
> (no tables, no RIDs) whose engine runs the composition-registered providers
> (`cmd/oikumenea/search_providers.go` — person, languoid, location, institution, company,
> publication, scholarship) in fixed lexicographic type order, each gated by `pep.AllowedAnywhere`
> on its read permission and trimmed through its R‑30 `Visibility` (person is `PreTrimmed`:
> `VisiblePersonIDsForSubjectSearch` trims in SQL). Pagination is a composite keyset token (one
> opaque cursor per non-exhausted provider; cursors advance over raw pre-trim rows — short pages
> possible, skips impossible). The ⌘K palette now calls it (`api.search.searchObjects`, typed TS
> SDK) — the fan-out cache and its "no server-side search" comment are deleted; RID-paste /
> Navigate / Actions / recents preserved. **Deviations from the fix sketch:** a `perTypeLimit`
> arg (default 5) so one palette request returns a per-type slice instead of one type flooding the
> page; hits are grouped by type (no relevance rank — deliberate, D-UnifiedSearch); `types` filter
> is CSV, not a Conjure list. Acceptance proven by `internal/search/search_integration_test.go`
> (deep person past the old 100-row window found; unreadable person absent; permission-lacking
> subject gets zero rows of that type; person hits ≡ `ListVisiblePersons`; multi-provider token
> walk exact) — the per-type arms are the unchanged R‑21 queries on their EXPLAIN-proven GIN
> indexes. Decision: **D-UnifiedSearch** ([decisions.md](decisions.md)); module doc
> [modules/search.md](../modules/search.md). `EntitySelect`/`explore/[type]` migration recorded
> there as an open seam.

**Evidence.** Per-type search is in good shape after R‑21: `SearchPersons`
(`internal/person/adapters/queries/person.sql`, trigram GIN, keyset, D-PersonSearch — see
`api/person.conjure.yml` `query` param docs) plus the five surfaces generalized in migration
`20260601000037_search_generalization.sql` (languoids, locations, organizations shared by
education+company, publications, scholarships — each a STORED `search_text` + `pg_trgm` GIN). But
**no endpoint searches across types**: all 24 Conjure services (`api/*.conjure.yml`) are
type-scoped; there is no `SearchService`/`ObjectService` contract. The web command palette
(`web/src/components/CommandPalette.tsx`) says it outright:

> `// ── fan-out object cache (no server-side search exists; we fetch one page per type and filter in the`
> `// browser). Module-level so it survives palette re-opens within a session; short TTL keeps it fresh. ──`

and builds its index with `const search = def.list!.search ?? "?pageSize=100"` — one first-page
GET per `EXPLORABLE_TYPES` entry, cached 60 s, substring-matched client-side.

**Why it matters at target scale.** At 1M+ persons and 10⁵–10⁷-row reference sets, "search the
first 100 rows per type" is not degraded search — it is a UI that *looks* like Gotham's entry
point while silently not finding almost anything. The analyst workload starts at a search box;
today that box finds an object only if it happens to sort into the first page of its type's
unfiltered list. Meanwhile the server-side trigram indexes that R‑21 built sit unused by the one
surface users would reach first. This is also a quiet correctness trap: an operator who searches
a sanctioned name, gets no hit, and concludes "not in the registry" has been misled by
architecture.

**Fix sketch.**
1. Add one Conjure contract (e.g. `api/search.conjure.yml`, `SearchService.searchObjects`:
   `query`, optional `types` filter, keyset page token) returning typed hits
   `{rid, objectType, label, snippet}` — RIDs are self-describing, so a hit needs no per-type
   response shape.
2. Implement as a **fan-in over the existing per-module search queries** (each already indexed
   and keyset-paginated) — not a new global index table. Modules register a `SearchProvider`
   (name, search func, required read scope) at composition time in `cmd/oikumenea/main.go`,
   consistent with the existing late-bound seam pattern (`LocationLookup`, `WatchlistLookup`).
3. Trim per provider via the R‑30 visibility adapter (blocking dependency — do not ship
   untrimmed).
4. Point the ⌘K palette (and the explorer's search boxes) at it; delete the client-side fan-out
   cache.

**Acceptance.** A palette query for a person on page ≥ 2 of the directory returns the hit; a
subject without the relevant read scope does not receive it; `grep -n "no server-side search"
web/src/components/CommandPalette.tsx` no longer matches; EXPLAIN on the new endpoint's per-type
arms shows the existing trigram indexes (no new seq scans at 10⁶ rows).

### <a id="r-27"></a>R‑27 — No links/search-around API: the object graph is a client fan-out over a hand-authored registry  **[high]**

> **RESOLVED — Phase 15 (2026-07-13).** `api/links.conjure.yml` → `LinkService.getObjectLinks`
> (`GET /links/v1/objects/{rid}/links`) + depth‑1 `searchAround`, implemented as the sketched fan-in:
> a new thin `internal/links` module (no tables, no RIDs) whose engine, for the queried RID's decoded
> object type, runs one keyset query per incident **link arm** over the reified link tables — table +
> endpoint columns supplied by a composition-time **link `Descriptor`** registry
> (`cmd/oikumenea/link_descriptors.go`), each descriptor's `(service,code)` validated against the
> drift-proof `pkg/rid` link-type registry (R‑28). Each arm is gated by `pep.AllowedAnywhere` on its
> read permission and neighbor rows trimmed through the neighbor type's R‑30 `Visibility` (person →
> person-scope, unit → shadow gate, else → catalog). The engine's **`MustBeBound` coverage
> assertion** joins main.go's boot seam loop and fails startup unless **every** kind=link RID type is
> registered **or** explicitly exempt — the drift guard (38 registered, 8 documented exemptions), so a
> link table a new milestone adds appears in `/o/[rid]` and `/graph` without touching `web/`.
> Pagination is a composite keyset token (one cursor per non-exhausted arm; cursors advance over raw
> pre-trim rows). The web `resolveLinkGroups` (object page + graph explorer through it) now calls
> `api.links.getObjectLinks` — the ~19-GET fan-out and its swallow-to-empty errors are gone; the
> `links[]` arrays become display-only hints. **Deviations from the fix sketch:** the union runs as a
> per-arm query loop (a logical union) rather than one SQL UNION statement — each arm still hits its
> own endpoint index. Acceptance proven by `cmd/oikumenea/links_integration_test.go` (coverage guard;
> memberships+kinships+polymorphic held_by in one call; per-arm permission gate; unreadable neighbor
> trimmed; person/company polymorphic holder resolution; multi-page token walk exact). Decision:
> **D-LinkTraversal** ([decisions.md](decisions.md)); module doc [modules/links.md](../modules/links.md).
> **Update (2026-07-16): server-side neighbor labelers delivered** — every named neighbor type resolves
> a `targetLabel` locale→text map (D-i18n) via a batch labeler (person name variants; else base
> name/title overlaid with `i18n_translations`), so link/graph rows show real names; `TestNeighborLabels`
> covers it. Depth‑2 search-around remains the open seam.

**Evidence.** The universal object page (`web/src/app/(dashboard)/o/[rid]/page.tsx`) and the
graph explorer (`web/src/components/ontology/GraphExplorer.tsx`) both resolve an object's
relationships via `resolveLinkGroups` (`web/src/lib/api/browser.ts`) — which iterates the type's
hand-written `links[]` array in `web/src/lib/ontology/registry.ts` (1,247 lines; 36 `targetType`
link entries) and fires **one HTTP GET per declared link collection** (`Promise.all` over
`api.request("GET", l.path(id))`, errors swallowed to empty groups). Expanding a single person
issues ~20 requests (memberships, orders, documents, six M14 relationship kinds, ~10 education
collections, …). There is no backend endpoint that answers "what links does RID X have" — even
though every reified link table already encodes its type in its own RID (kind=2) and its module
prefix, and `platform_rid_types` enumerates them.

**Why it matters at target scale.** Three compounding failures. (1) **Completeness:** a new link
table is invisible to the explorer, the dossier, and the graph until someone hand-edits
`registry.ts` — the M18–M50 build-out added link types faster than the registry tracked them
(see R‑28's drift), so the "object explorer" silently under-reports relationships, which for a
watchlist/registry product is the worst failure mode available. (2) **Cost:** ~20 requests per
node-expand means a 3-hop investigation graph is hundreds of round-trips; Gotham-style
search-around (depth 2, "any path between these two people?") is architecturally unreachable
from the client side. (3) **Trust:** `resolveLinkGroups` swallows per-endpoint errors into empty
groups, so a 403/500 renders as "no relationships".

**Fix sketch.**
1. Backend **link registry**: each module registers its link tables' metadata (link type token,
   endpoint columns, target object types, temporal columns) at composition time — the Go
   counterpart of `registry.ts`'s `links[]`, derived from the same `pkg/rid` registry so it
   cannot drift (pairs with R‑28).
2. One Conjure endpoint `getObjectLinks(rid)` returning grouped `{linkType, direction, rows:
   [{linkRid, targetRid, targetLabel, attrs…}]}` — implemented as a UNION over the registered
   link tables filtered by the RID's endpoint columns (each already indexed by its FK / partial
   unique indexes).
3. Depth-1 `searchAround(rid, linkTypes?)` on top of it; depth-2 as a follow-up only with
   measurements.
4. Visibility-trim rows through the R‑30 adapter; per-link-type permission codes where the module
   already defines them.
5. Re-point `resolveLinkGroups` at the new endpoint; the web `links[]` arrays become
   display-only hints (labels, column choices), not the traversal source of truth.

**Acceptance.** Expanding a person in `/graph` issues O(1) requests, not ~20; a link table added
by a new milestone appears in `/o/[rid]` without touching `web/`; a subject lacking a link's read
permission sees neither the link nor the neighbor; a two-hop expand of a 50-neighbor node
completes in < 1 s against the M49-scale dataset.

### <a id="r-28"></a>R‑28 — Four hand-synced ontology mirrors, no coherence check; the one guard is dead code that docs claim runs at boot  **[high]**

> **RESOLVED — Phase 13 (2026-07-12).** (1) `rid.AssertMatches` is wired into oikumenea boot
> (`cmd/oikumenea/main.go`, right after `platform.Bootstrap`) — the dead code is now live and
> `conventions.md`'s "boot-asserted equal" is true; proven by `pkg/rid/assertmatches_integration_test.go`
> (passes on the seed, fails on a tampered `platform_rid_types`). (2) The web mirror is now GENERATED
> from `pkg/rid` (`tools/gen-ontology-mirror` → `web/src/lib/ontology/generated-rid.ts`), consumed by
> `rid.ts`, drift-gated by `scripts/gen-ontology-mirror.sh --verify` + `.github/workflows/ontology-mirror.yml`.
> The drift is gone (services 15/16/17/19 present, 12=`location`, GONE education tokens dropped, finance
> RID resolves). `registry.ts` re-keyed onto the generated tokens (only rank `rank_system`→`system`
> changed; one collision `finance`/`account`→`finance_account`). (3) The coherence test is
> `pkg/rid/ontology_doc_test.go`. **Deviation from the fix sketch:** it runs **doc→Go** (every numeric
> RID triple the catalog cites resolves to a real Go type), not Go→doc — empirically 63/143 core types
> are described by name in prose without a numeric RID, so a Go→doc numeric gate would be ~63 false
> failures. doc→Go is the deterministic half (one documented exception: `15,1,1`, which the catalog
> cites only to say it is deliberately absent under M41).

**Evidence.** The type registry exists in four places kept equal by hand: (1) the SQL seed
`oikumenea.platform_rid_services` / `platform_rid_types` (migration
`20260601000000_schema_bootstrap.sql`); (2) the Go mirror `pkg/rid/registry.go`
(`serviceNames` — 19 services — + `typeNames`, ~130 entries); (3) the prose catalog
[ontology-mapping.md](../ontology-mapping.md); (4) the web console's
`web/src/lib/ontology/rid.ts` (`SERVICE_NAMES`, `TYPE_TOKENS`) + `registry.ts`. Two independent
failures:

- **The drift guard is dead code and the docs lie about it.** `pkg/rid.AssertMatches`
  (`registry.go`, `func AssertMatches`) is written precisely to compare (2) against (1) — and has
  **zero call sites** (`grep -rn "AssertMatches" --include="*.go"` → only `pkg/rid/registry.go`
  itself). Yet its own header comment ("AssertMatches verifies the two agree at boot so they
  cannot drift") and `docs/architecture/conventions.md` § Resource identifiers ("mirrored in
  `pkg/rid` **(boot-asserted equal)**") both state the assertion runs. A reader — or this
  repo's own convention of trusting `conventions.md` — would conclude a protection exists that
  does not.
- **Mirror (4) has already drifted, proving the risk is real.** `rid.ts` `SERVICE_NAMES` stops at
  service 18 minus gaps: **company (15), religion (16), vehicle (17), finance (19) are absent**,
  and 12 is labeled `"geo"` where the Go registry says `location`. `TYPE_TOKENS` still carries
  the pre-M41 education types `14/1/1 institution`, `14/1/2 education_unit`, `14/1/7 unit_kind`,
  `14/2/1` — which `registry.go` explicitly marks GONE ("types 1/2/7 and link 1 are GONE here",
  unified onto the tenant org-graph). Consequence today: the console cannot decode or route a
  RID from four shipped modules (paste a finance account RID into ⌘K → unknown type), and would
  mis-token a resurrected education code.

**Why it matters at target scale.** The RID plane is the spine of everything this review's other
findings want to build (generic search hits, link traversal, action refs are all "just RIDs"
*because* the registry is trustworthy). Hand-sync across four mirrors fails exactly when the
system grows fastest — which is what happened. And a documented-but-unwired safety check is worse
than none: it suppresses the vigilance that would otherwise catch drift.

**Fix sketch.**
1. Wire `rid.AssertMatches` into oikumenea boot (composition root, next to the existing
   boot-time schema-version check; fail fast on mismatch), and fix the `conventions.md` wording
   only if the wiring is deferred — never claim it before it runs.
2. Generate mirror (4) from mirror (2): a small `go run ./tools/...` generator emitting
   `SERVICE_NAMES`/`TYPE_TOKENS` (and the skeleton type list `registry.ts` keys off) from
   `pkg/rid`'s tables, checked in CI (`git diff --exit-code` after regen). Do not hand-edit the
   TS tables again.
3. Add a test asserting every `(service,kind,type)` in the Go registry has a row in
   `ontology-mapping.md`'s §1/§2 tables (parse the markdown table's RID-triple column) — cheap,
   and turns the "binding catalog" claim into a checked invariant.
4. Backfill the current drift (add 15/16/17/19, rename 12, drop the GONE education tokens) via
   the generator, not by hand.

**Acceptance.** Boot fails against a DB whose `platform_rid_types` was tampered with;
`AssertMatches` has a caller in `cmd/oikumenea` (grep); regenerating the TS mirror is
byte-identical in CI; a finance account RID pasted into the console resolves to a labeled type;
the markdown-coherence test fails when a migration seeds a type the doc doesn't list.

### <a id="r-30"></a>R‑30 — Read visibility is bespoke per module; every cross-type surface is blocked on a per-type adapter that doesn't exist  **[medium]**

> **RESOLVED — Phase 14 (2026-07-13).** `internal/authorization/scope` (D-VisibilityScope):
> `Visibility.ReadableIDs(ctx, subject, isAdmin, candidateIDs) → ids` (order-preserving subset,
> admin short-circuit) with exactly the three sketched implementations — `NewPersonScope` (over a
> NEW membership batch probe `SubjectReadablePersonsAmong`, the `unnest` variant of
> `SubjectCanReadPerson`; proven ≡ the Go `ReachSet` oracle by a new section (b2) in membership's
> randomized `TestReachDifferential`), `NewUnitScope` (module-supplied id→owning-unit/shadow map +
> the existing `FilterVisibleUnits`; drops unmapped candidates — fail closed), `NewCatalogScope`
> (identity; the permission gate is the whole decision). Implementations take injected funcs, so
> authorization still imports no other module; `pep` gained the non-erroring `AllowedAnywhere`
> probe. Registration is one pass with the R‑26 search registry (`Register(provider, visibility)`
> — a provider without a visibility is a boot error, and the engine joined main.go's `MustBeBound`
> seam loop), satisfying "adding a type without registering visibility fails composition".
> **Deviation from the fix sketch:** the batch `ReadableIDs` form only — the `ReadScopeFor`
> predicate variant is deferred until a consumer (R‑27) needs it. Existing endpoints untouched
> (additive, as specified). Decision: **D-VisibilityScope** ([decisions.md](decisions.md)).

**Evidence.** The PDP core is generic and strong: `Decide`/`Require` over the unit-DAG closure +
grant cache (`internal/authorization/domain/pdp.go`, `internal/authorization/pep/pep.go`), and
`FilterVisibleUnits` for the shadow gate. But **row-level read trimming is re-invented per
module**: person has its own D-PersonReadScope projection (`internal/person/application/service.go`
— `MembershipReader.VisiblePersonIDsForSubject` seam, `ReadablePerson`, `ListVisiblePersons`,
a membership semi-join); tenant lists run `FilterVisibleUnits`; reference catalogs are
coarse-gated by a single permission at the endpoint with no row trim. There is no shared
interface answering the one question a generic surface needs: *given an object RID and a
subject, may the subject read it* — equivalently, *map this object to its governing unit(s) and
read-permission code*.

**Why it matters at target scale.** R‑26 and R‑27 cannot ship without this: a unified search or
links endpoint that returns rows the per-module endpoints would have trimmed is a
permission-bypass, and one that conservatively returns nothing is useless. This finding is the
**load-bearing prerequisite** — sequenced before both in the roadmap. It is also the honest cost
of the (correct) decision to keep row security in the app layer rather than RLS: that decision
concentrates the obligation into exactly this adapter.

**Fix sketch.**
1. Define one interface in the authorization module (e.g. `VisibilityScope`:
   `ReadableIDs(subject, objectType, candidateIDs) → ids` plus a batch
   `ReadScopeFor(subject, objectType) → predicate`), with three canonical implementations
   matching today's real policies: person-scope (membership semi-join), unit-scope
   (`FilterVisibleUnits` + owning-unit mapping), catalog-scope (permission gate, no row trim).
2. Modules register their object types against one of the three at composition time (the same
   registration pass as R‑26's `SearchProvider` / R‑27's link registry — one registry, three
   facets).
3. Refactor nothing that works: existing per-module endpoints keep their current code paths;
   the adapter is *additive*, consumed by the new cross-type surfaces (and available for future
   consolidation).

**Acceptance.** A differential test per registered type: for a fixed subject, the ids returned
by the adapter equal the ids the module's own list endpoint returns (same fixtures); the R‑26
search endpoint returns zero rows of a type whose read permission the subject lacks; adding a
type without registering visibility fails composition (not silently untrimmed).

### <a id="r-29"></a>R‑29 — Action *types* don't exist: generic `type_code 0`, free-text names, no catalog — while the order module shows the full pattern working  **[medium]**

> **RESOLVED — Phase 16 (2026-07-13).** New leaf `pkg/action` (imports only `pkg/rid`): a **286-row
> action-type catalog** `{code, service, targetType, permission}` keyed by the dotted `audit_log.action`
> code. Built exactly as the fix sketch's item 1 (a registry mirrored in Go, asserted like R-28) —
> derived from the **actual emit sites** (runtime capture of every audited write during the full suite
> ∪ a static scan) so it is complete against what the code emits. Item 2: `audit.Service.Record` now
> rejects an unregistered action (`action.Validate`; kept out of the stdlib-only `audit/domain`) — the
> full integration suite (61 pkgs) passes with the gate on, i.e. every emitted action is catalogued, and
> `pkg/action`'s `TestValidateGate` proves a typo is rejected. Item 3: `AuditService.listActionTypes`
> (`GET /audit/v1/action-types`) serves the catalog (Go + TS SDK regenerated). Item 4: the order
> module is named the reference pattern in [ontology-mapping.md §3.1](../ontology-mapping.md), whose
> **generated catalog table** the coherence test `pkg/action/catalog_doc_test.go` asserts equal to the
> registry; the audit RID stays kind=action/type 0 (expand-only — no retrofit). **Deviations:**
> `permission` is module-granular (the finding's "required permission" at write-permission fidelity;
> per-action codes are an open seam). **Update (2026-07-16): the parameter-schema seam is now closed.**
> Each `ActionType` optionally names its Conjure request type (`RequestType`), and its `parameters`
> (`{name, type, required, docs}`) are **derived from the Conjure IR** by `tools/genactionparams`
> (`scripts/gen-action-params.sh` → generated `pkg/action/params_gen.go`, drift-guarded by
> `TestRequestTypesResolve`) — single-sourced, never hand-authored. `listActionTypes` returns them and
> the console renders them read-only (audit catalog + `/o/[rid]` Actions panel). Descriptive only (no
> write-time argument validation — the wrong layer). First tranche annotated (authz/tenant/membership/
> order); remaining modules are expand-only follow-on. A schema-driven **invocation** form was
> deliberately *not* built (it would be the generic framework this finding warned against, and would
> duplicate the typed bespoke forms). Decision:
> **D-ActionTypes** ([decisions.md](decisions.md)). The console actions-panel re-point is a light
> follow-up (the endpoint exists).

**Evidence.** By design (D-Audit, migration `20260601000000_schema_bootstrap.sql`: "Action RIDs
use the generic type_code 0 ('action') — the specific action name lives in audit_log.action"),
every service seeds exactly one `(svc, 3, 0, 'action')` row and every audited write mints a
kind=3 RID of that one type; the *actual* action identity is `audit_log.action text NOT NULL`
("e.g. assignment.grant, unit.transition" — migration `20260601000001_audit_log.sql`, which also
states "the audit log IS the action ledger"). [ontology-mapping.md §3](../ontology-mapping.md)
lists the actions — as prose, with no machine counterpart: no table of action types, no
parameter schemas, no registry a client could enumerate. Contrast the **order module**, which is
a complete Foundry-style action type in all but name: `order_order_types` is a catalog with a
typed `effect` CHECK (`membership-start | membership-end | rank-change | record-only`, migration
`20260601000010_order.sql`), `IssueOrder` (`internal/order/application/service.go`) executes one
validated all-or-nothing mutation whose effects apply via domain events in the same transaction,
and `order_item_id` provenance is the `CAUSED_BY` lineage.

**Why it matters at target scale.** Free-text action names are write-time convention with no
read-time contract: nothing prevents `assignment.grant` vs `assignment.granted` drifting between
modules, nothing lets an operator (or the console's `ObjectActions` panel) *discover* what
actions exist for a type, and audit analytics ("all actions of type X on objects of type Y this
quarter") depend on string hygiene across ~26 modules. Foundry's action types earn their keep
precisely at this scale: they make mutations enumerable, validatable, and auditable *by type*.
The repo already pays the cost of the pattern (per-action permission codes, audit rows, Conjure
endpoints per action) without the payoff of the catalog.

**Fix sketch.** Deliberately modest — a registry, not a framework:
1. Add an action-type registry alongside the RID type registry (extend `pkg/rid`'s tables or a
   sibling `platform_action_types` seed: `code` like `assignment.grant`, owning service, target
   object type, required permission) mirrored in Go and asserted like R‑28.
2. Make `audit_log.action` validated against it at write time (app-layer, in the audit writer —
   no schema change to the partitioned table).
3. Expose `listActionTypes` (one small Conjure endpoint) so the console's actions panel is
   registry-driven server-side, mirroring how R‑27 treats links.
4. Name the order module in `ontology-mapping.md §3` as the reference pattern; **do not**
   retrofit per-action RID type codes into existing audit rows (kind=3/type 0 stays valid for
   history — expand-only).

**Acceptance.** An audited write with an unregistered action name fails in tests; the registered
action list equals ontology-mapping §3's list (coherence test, same style as R‑28's); the console
enumerates a type's actions from the endpoint, not from `registry.ts` alone.

### <a id="r-31"></a>R‑31 — No temporal story beyond scattered ledgers; §4.1 ratifies the gap without bounding it  **[medium, decision challenge]**

> **RESOLVED — Phase 17 (2026-07-14).** [**D-Temporal**](decisions.md#d-temporal--a-three-tier-link-history-classification-native-validity-by-default-plus-getobjecthistory-over-the-audit-ledger)
> added to decisions.md with the three-tier table (a native-validity / b audit-served object history /
> c history-exempt). The user chose **aggressive native validity**: tier (a) is the **mandate** for
> relationship Links, not just a description of current state. `valid_from`/`valid_to` (+ an inline
> range CHECK) were **folded directly into each of the thirteen** previously-undated relationship Links'
> original `CREATE TABLE` (edit-in-place + DB rebuild, the unreleased-build-out convention — like R-32's
> shape CHECKs), leaving a **closed six-member** tier-(c) exempt set (`locale_language`, `unit_language`,
> `written_in`, `curriculum_item`, `course_prerequisite`, `has_ethnicity`). The boundary is enforced
> executable by `cmd/oikumenea/temporal_tiers_test.go` (`TestTemporalTierCoverage` fails on any
> unclassified kind=Link type; `TestValidityLinksHaveDatingColumn` fails if a tier-(a) Link's DDL lacks
> a validity column) — the drift guard §4.1 lacked. The cheap capability shipped:
> **`AuditService.getObjectHistory(rid)`** (`GET /audit/v1/objects/{rid}/history`) reads the ledger back
> as a reverse-chronological timeline, gated by `audit.read` with **before/after redacted unless the
> caller holds the sensitive-reader capability** (`authorization.SensitiveReadPermissions()` / instance
> admin — the D-DataScope special-category bar). `docs/development-process.md`'s design gate now requires
> a tier declaration for every new Link; §4.1's verdict points at D-Temporal. **Acceptance met** —
> `getObjectHistory` returns the ordered change list for a person whose rank changed twice
> (`TestGetObjectHistory*` in `cmd/oikumenea/audit_history_integration_test.go`), permission-gated and
> redaction-gated. As-of reconstruction + full bitemporality stay named seams, not implied.

**Evidence.** [ontology-mapping.md §4.1](../ontology-mapping.md) ("Temporal Links vs soft-delete
(**the biggest gap**)") ratifies the divergence: the ontology ideal is validity on every link
with history never overwritten; the repo has `deleted_at` + `updated_at` (current-state only) and
"reconstructs relationship history from order provenance, domain events, and the audit log."
What exists is real but scattered: effective-dating on membership (`effective_from/to`) and
person addresses (`valid_from/to`) and some vertical links; append-only lifecycle ledgers
(`tenant_unit_lifecycle_events`, `tenant_unit_code_events`, org events); and — the key
under-used asset — the audit ledger is **already per-object queryable**:
`audit_log_target_idx ON oikumenea.audit_log (target_type, target_id)` (migration
`20260601000001_audit_log.sql`) with `before/after jsonb` on every audited write. Yet **no
endpoint reads any of it back as history**: no `history`/`as-of`/`versions` route exists in any
Conjure contract, so "what did this person's record say on date X" and a Gotham dossier timeline
are unanswerable through the API despite the data existing. And §4.1 sets no boundary: which
object types owe history, which links owe validity dating, and which are exempt is undecided, so
each new milestone re-decides ad hoc (some M18–M50 links got `valid_from/to`, some got nothing).

**Why it matters at target scale.** For a registry whose stated identity includes watchlists,
sanctions and regulatory exposure, *when we knew something* is not a nice-to-have — it is what
distinguishes an intelligence platform from a CRUD directory, and it is unrecoverable
retroactively for any table that overwrote state before dating was added. The unbounded
divergence also grows monotonically: every new undated link is future migration debt.

**Fix sketch.** Decision first, cheap capability second:
1. **D-Temporal** amendment in [decisions.md](decisions.md) (needs the user): a three-tier
   classification — (a) links that carry native validity (`valid_from/to` — the D-ResourceIdentifiers
   definition §4.1 already cites), (b) objects whose history is served from the audit ledger,
   (c) explicitly history-exempt reference catalogs. New milestones declare the tier at design
   time, same as they declare Object/Link/Action kind today.
2. Ship the cheap first capability: `getObjectHistory(rid)` — a paginated read over
   `audit_log (target_type, target_id)` returning `{at, action, actor, before, after}`. The
   index exists; this is one endpoint, gated behind a sensitive-read permission (before/after
   can carry pii up to the D-DataScope ceiling).
3. Timeline rendering in the console consumes it; as-of *reconstruction* (folding before/after
   into a point-in-time view) stays a later seam — record it as such in §4.1 rather than
   implying it.

**Acceptance.** decisions.md contains D-Temporal with the tier table; `docs/development-process.md`'s
design gate mentions the tier declaration; `getObjectHistory` returns the audited change list for
a person whose rank changed twice, in order, permission-gated; §4.1's verdict is updated to point
at the decision instead of "additive seam" hand-waving.

### <a id="r-32"></a>R‑32 — Polymorphic link ends are unverifiable and invisible to generic traversal  **[low]**

> **RESOLVED (shape CHECKs) — Phase 13 (2026-07-12).** A CHECK per polymorphic end
> (`finance_account_holders`, `vehicle_registrations`, `company_foundings`, `company_shareholdings`)
> using the IMMUTABLE `rid_service`/`rid_kind`/`rid_type` decoders; the `::uuid` cast also rejects a
> malformed id. Folded **inline into each `CREATE TABLE`** in the existing migrations (finance 0034,
> vehicle 0027, company 0022 ×2) rather than a separate ALTER migration — this build-out is unreleased,
> so migrations are edited in place + the DB rebuilt (repo convention). Reject-path tests added to the
> three vertical integration suites (a wrong-type holder id fails at the DB with SQLSTATE 23514).
> **Deviation from the fix sketch:** the sketch assumed a company
> holder is a service-15 RID; the live data proves a company holder is a **tenant-organization RID
> `(4,1,6)`** (M41/D-UnifiedOrgGraph — a company IS a tenant org, no own company object RID), so both
> ends pin the full triple: person `(6,1,1)`, company `(4,1,6)`. **Fix-sketch item 2 RESOLVED —
> Phase 15 (2026-07-13):** each polymorphic end is declared in the R‑27 link `Descriptor` registry
> (`cmd/oikumenea/link_descriptors.go`, `personOrCompany` — one target per discriminator), so
> `getObjectLinks` traverses these holder/owner edges in both directions (`TestPolymorphicHolder`).

**Evidence.** The deliberate F-014 pattern for person-or-company link ends is
`(holder_kind text CHECK (IN ('person','company')), holder_id text NOT NULL — no FK)`:
`finance_account_holders` (migration `20260601000034_finance.sql`), `vehicle_registrations`
(`owner_kind`/`owner_id`, migration `20260601000027_vehicle.sql`), `company_foundings` /
shareholdings (migration `20260601000022_company.sql`). Credit where due: the kind is
CHECK-constrained, the pair is partial-indexed (`…_holder_idx (holder_kind, holder_id) WHERE
deleted_at IS NULL`), and the audit log's `target_id` uses the same documented convention. What's
missing is any integrity on the **id itself**: nothing validates that `holder_id` is a
well-formed RID, that its decoded service/kind/type agrees with `holder_kind`, or that the row
exists — a typo'd or dangling holder is stored silently. And because the columns are `text` with
no FK, these edges are exactly the ones a generic link registry (R‑27) cannot discover from the
schema; they must be declared.

**Why it matters at target scale.** Finance and vehicle ownership edges are precisely the ones an
investigation traverses ("who holds accounts at this bank", "what does this person own") — the
one place a dangling edge is worse than a missing one. The risk is bounded today (single write
path per table, RIDs come from the same system), which is why this is low — but it compounds
with import industrialization (M49), where holder ids arrive from external pipelines.

**Fix sketch.**
1. Add a CHECK per polymorphic end using the existing immutable decoders — e.g.
   `CHECK (holder_kind <> 'person' OR (rid_service(holder_id::uuid) = 6 AND rid_kind(holder_id::uuid) = 1))`
   (and the company analog) — cheap, expand-only, catches malformed/mistyped ids at the door
   (existence still app-enforced, as now).
2. Declare each polymorphic end in the R‑27 link registry with its kind-discriminator so generic
   traversal includes them (both directions — "accounts held by X" requires the
   `(holder_kind, holder_id)` index that already exists).
3. One import-path test per table: a holder id of the wrong RID type is rejected.

**Acceptance.** Inserting a `holder_kind='person'` row whose `holder_id` decodes to a company RID
fails at the DB; `getObjectLinks` on a person surfaces their finance/vehicle edges; `atlas
migrate lint` stays clean (additive CHECKs only).

### Explicitly NOT recommended
- **A generic EAV / single-object-store rewrite.** The typed-table-per-object design is the
  repo's core strength and matches how Foundry itself backs ontology objects with concrete
  datasources. The gap is a service layer *over* the tables, not the tables.
- **A DB-driven dynamic runtime ontology** (types defined in rows, schema at runtime). Keep the
  ontology compile-time in Go + migrations; *generate* the mirrors from it (Phase 13). The
  fixed pipeline (idea → decided → designed → …) is the type-creation workflow.
- **Replacing the PDP with OpenFGA/SpiceDB.** Evaluated and deferred 2026-07-03
  ([authorization.md](../modules/authorization.md) § "The model in Zanzibar/FGA notation" — the
  DSL is documentation only, no engine consumes it); the 2026-07/08 cycles removed the actual
  bottleneck. R‑30 is an adapter over the existing PDP, not a new engine.
- **A graph database** for search-around. Postgres over the existing link tables + closure
  serves depth-1/2 traversal at the stated scale; revisit only with measurements from Phase 15.
- **Elasticsearch / external search infrastructure.** The R‑21 trigram/STORED-column pattern
  already won this trade-off in-database; Phase 14 federates it, it does not replace it.
- **Blanket bitemporality across all tables.** R‑31 exists precisely to *scope* history; adding
  transaction-time axes everywhere is the failure mode the tier decision prevents.
